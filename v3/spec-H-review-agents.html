Review Agents
A critique layer between every agent handoff. Every artifact is reviewed before the next phase begins. The loop runs up to 3 times before human escalation — preventing both infinite loops and low-quality output reaching downstream agents.
5 Review Agents Version: 3.0 Status: Draft May 2026

The Universal Pattern #overview

Every phase in the FORGE V3 pipeline follows the same structure. A Producer Agent creates an artifact. A Review Agent critiques it. If the review finds issues, revision tasks are created and the Producer picks them up. This loop runs up to three times. If the artifact is still not approved after three cycles, human escalation is triggered.

Core Principle
Review Agents are not gatekeepers — they are critics. Their job is to produce structured, actionable feedback that makes the artifact better. They never block work permanently. They either approve or generate revision tasks that the Producer resolves.

The pattern is identical across all five review agents. Only the rubric changes — what the agent looks for in a spec is different from what it looks for in code, but the loop, the escalation logic, and the task schema are the same.

The Review Loop #loop

// The universal review loop — identical for all 5 review agents Producer Agent creates artifact ↓ Review Agent evaluates artifact against rubric ↓ ┌────APPROVED────────────────────────────────────┐ │ │ │ ISSUES FOUND │ │ ↓ │ │ Revision tasks created (one per issue) │ │ Each task: issue_type, description, severity │ │ ↓ │ │ Producer Agent picks up revision tasks │ │ Revises artifact to address each issue │ │ Resubmits full artifact for re-review │ │ ↓ │ │ review_cycle_count += 1 │ │ ↓ │ │ if review_cycle_count < 3 → loop back │ │ if review_cycle_count == 3 → HUMAN ESCALATION │ │ │ └────────────────────────────────────────────────────┘ ↓ Next phase begins (next Producer Agent dequeues)

The review_cycle_count is stored as a field on the parent task in Jira. Every time the Review Agent finds issues and creates revision tasks, the count increments. At count 3, the Scheduler flags the task as HUMAN_REVIEW_REQUIRED and notifies the relevant stakeholder — product owner for spec, tech lead for architecture and code, QA lead for test cases.

Why 3 cycles?
One cycle is too few — a first draft almost always needs refinement. Unlimited cycles risks infinite loops if the Producer and Reviewer disagree on a subjective point. Three cycles is enough to converge on quality while protecting against deadlock. If three expert AI review cycles cannot resolve an issue, a human should be involved.

What the Review Agent Has Access To

Every Review Agent receives the same context package:

  • The original requirement — the PM's one-liner from the Spec Generator conversation. This is the ground truth every artifact is measured against.
  • The artifact being reviewed — the full output of the Producer Agent in this cycle.
  • All previous review cycles — what was flagged before and how the Producer addressed it. This prevents the Reviewer from raising the same issues repeatedly.
  • Upstream approved artifacts — a Code Review Agent also has the approved architecture and approved test cases, so it can check the code against all three.

01 — Spec Review Agent #spec-review

R1
Spec Review Agent
Reviews: Functional Specification
Claude Sonnet API CPU droplet 1,024 token budget Max 3 cycles
Reviews
The functional specification produced by the Spec Generator Agent — scope, out-of-scope, user flows, performance expectations, integration requirements.
Context
Original PM requirement · Current spec · Previous review cycles and how they were addressed
Model
Claude Sonnet API — same model as Spec Generator, so the reviewer understands the spec's language and intent
Output
APPROVED — pipeline advances to Architecture Agent. OR: structured list of issues, each becoming a revision task for the Spec Generator.

Spec Review Rubric #spec-rubric

COMPLETENESS
Does the spec cover all user-facing scenarios mentioned or implied by the original requirement? Are edge cases documented? Are error states described?
AMBIGUITY
Are there any requirements that could be interpreted in two different ways? Any undefined terms? Any "should" vs "must" inconsistencies?
CONTRADICTIONS
Does any requirement contradict another? For example: "must be real-time" and "no WebSocket dependency" in the same spec.
SCOPE CREEP
Does the spec include features not in the original requirement? Scope creep inflates the task list and delays delivery.
OUT-OF-SCOPE GAPS
Are the out-of-scope items explicit enough? Vague out-of-scope definitions lead to Architecture Agent guessing what to exclude.
TESTABILITY
Can each requirement be tested? "The system should be fast" is not testable. "p95 latency under 200ms at 100 concurrent users" is.
PM INTENT
Does the spec actually answer what the PM asked for? Compare the spec against the original one-liner and the conversation.

02 — Architecture Review Agent #arch-review

R2
Architecture Review Agent
Reviews: System Architecture + ADRs + Data Model + Interface Contracts
Llama-3.1-70B · H100 2,048 token budget Max 3 cycles
Reviews
System architecture document, data model, interface contracts, ADRs — all five Architecture Agent artifacts together.
Context
Original PM requirement · Approved functional spec · Current architecture artifacts · Previous review cycles
Model
Llama-3.1-70B on H100 — same model as Architecture Agent, giving the reviewer deep understanding of the design decisions made.
Output
APPROVED — pipeline advances to Code Task Generator. OR: structured issues, each becoming a revision task for the Architecture Agent.

Architecture Review Rubric #arch-rubric

SPEC COVERAGE
Does the architecture address every requirement in the approved spec? Any requirement without an architectural component is a gap.
TECHNOLOGY FIT
Are the technology choices appropriate for the scale, team, and requirements? Over-engineering (Kafka for 100 users) and under-engineering (SQLite for 10,000 concurrent writes) are both flagged.
SECURITY POSTURE
Are authentication, authorization, encryption at rest, encryption in transit, and input validation all addressed? Any obvious attack surface left unaddressed?
DATA MODEL INTEGRITY
Are all relationships correctly modelled? Are indexes defined for query patterns? Are constraints enforced at the database level, not just in application code?
INTERFACE COMPLETENESS
Does every task-to-task handoff have an explicit interface contract? Any implicit coupling between tasks is flagged.
ADR QUALITY
Does each ADR document the context, decision, consequences, and alternatives considered? ADRs without alternatives considered are incomplete.
SCALABILITY PATH
If the system needs to scale 10x, what breaks first? The architecture should acknowledge known bottlenecks even if not solving them in v1.

03 — Task Review Agent #task-review

R3
Task Review Agent
Reviews: Implementation Task List from Code Task Generator
Claude Sonnet API CPU droplet 1,024 token budget Max 3 cycles
Reviews
The full implementation task list produced by the Code Task Generator — task descriptions, file paths, interface references, dependencies, acceptance criteria.
Context
Original requirement · Approved spec · Approved architecture · Current task list · Previous review cycles
Output
APPROVED — tasks enter Jira as QUEUED, Test Case Generator begins. OR: issues flagged, revision tasks sent to Code Task Generator.

Task Review Rubric #task-rubric

ARCHITECTURE COVERAGE
Is there a task for every component, service, and interface defined in the architecture? Any architectural element without a corresponding task is a gap.
TASK ATOMICITY
Is each task small enough to be completed in one Code Agent session? Tasks that span multiple systems or require more than ~4,096 tokens to implement should be split.
DEPENDENCY CORRECTNESS
Are all dependencies between tasks correct? If Task B consumes an interface produced by Task A, is "Task B depends on Task A" explicitly set?
INTERFACE REFERENCES
Does each task reference the exact interface contracts from the architecture that it must implement or consume?
ACCEPTANCE CRITERIA
Does each task have testable acceptance criteria? "Implement the account service" is not testable. "GET /accounts returns paginated results with 200 OK" is.
FILE PATH VALIDITY
Do the file paths in each task match the directory structure implied by the architecture? No two tasks should write to the same file.
SEQUENCING
Can the tasks be executed in the order specified? Are there circular dependencies? Is the parallelism maximised given the dependency graph?

04 — Test Case Review Agent #testcase-review

R4
Test Case Review Agent
Reviews: Test case specifications from Test Case Generator
Claude Sonnet API CPU droplet 1,024 token budget Max 3 cycles
Reviews
Test case specifications for each implementation task — what to test, how to test it, what the expected outcome is, and what edge cases must be covered.
Context
Original requirement · Approved spec · Approved architecture · Approved task list · Current test cases · Previous review cycles
Critical role
Test cases are approved BEFORE the Code Agent writes a single line. The Code Agent receives approved test cases as a contract — it writes code that satisfies them. This enforces test-driven development across the entire pipeline.
Output
APPROVED — test cases locked, Code Agent begins. OR: issues flagged, revision tasks sent to Test Case Generator.

Test Case Review Rubric #testcase-rubric

COVERAGE
Is there at least one test case per acceptance criterion in the task? Does coverage include happy path, error path, and boundary conditions?
CORRECTNESS
Are the expected outputs in each test case actually correct given the architecture and spec? A test case with a wrong expected value is worse than no test case.
INDEPENDENCE
Can each test run independently without relying on the state left by another test? Tests that depend on execution order are fragile and should be split.
EDGE CASES
Are boundary values tested? Null inputs, empty collections, maximum values, concurrent access, timeout scenarios — these are where bugs hide.
INTERFACE ALIGNMENT
Do the test cases test the exact interface signatures defined in the architecture? A test that calls a method with the wrong signature will never pass.
DETERMINISM
Will each test produce the same result every time it runs? Tests that depend on external services, random values, or system time without mocking are not deterministic.
IMPLEMENTABILITY
Can a Code Agent actually write code that satisfies these tests? Tests that require impossible behaviour or contradict the architecture are flagged.

05 — Code Review Agent #code-review

R5
Code Review Agent
Reviews: Source code produced by Code Agent
Qwen2.5-Coder-32B · L40S 2,048 token budget Max 3 cycles Applies to bug fixes too
Reviews
Source code written by the Code Agent for any task — implementation tasks, bug fix tasks from Build Monitor, Log Monitor, or Performance Monitor.
Context
Original requirement · Approved architecture · Approved test cases · The code being reviewed · Previous review cycles
Scope
Applies to ALL code produced by the Code Agent — not just new feature code. Bug fixes from the Build & Test Monitor, Log Monitor, and Performance Monitor all go through Code Review before being committed.
Model
Qwen2.5-Coder-32B on L40S — same model as Code Agent, giving the reviewer the deepest possible understanding of the code's intent and patterns.
Output
APPROVED — code committed to customer branch. OR: issues flagged, revision tasks sent to Code Agent.

Code Review Rubric #code-rubric

SYNTAX & COMPILATION
Does the code compile and parse without errors? No undefined variables, no type mismatches, no missing imports.
INTERFACE COMPLIANCE
Does the code implement exactly the interfaces defined in the architecture? Any deviation — different method signature, different return type — is a blocking issue.
TEST CASE SATISFIABILITY
Would the approved test cases pass against this code? The reviewer traces through each test case mentally and flags any that would fail.
STYLE & CONVENTIONS
Does the code follow the patterns established in the existing codebase (from LoRA training)? Naming, error handling, logging, comment style.
SECURITY PATTERNS
Input validation, parameterised queries, no hardcoded credentials, proper error messages (no stack traces to the client), principle of least privilege.
CORRECTNESS
Does the code actually do what the task requires? Logic errors, off-by-one errors, incorrect business logic — these are caught here before the customer CI/CD runs.
UNNECESSARY CHANGES
Did the Code Agent modify files it was not supposed to touch? Any change outside the task scope is flagged and must be removed.

Review Task Schema #task-schema

When a Review Agent finds issues it creates one revision task per issue. Each task is a structured JSON object stored in Jira — the same task store used by all other agents. Review tasks are a distinct ticket type: REVIEW_REVISION.

// Review Agent output — one object per issue found
{
  "review_id":        "REV-0042",
  "parent_task_id":   "SPEC-001",          // the artifact being revised
  "reviewer":         "spec_review_agent",
  "cycle":            1,                   // which review cycle this is
  "status":           "ISSUES_FOUND",      // or APPROVED

  "issues": [
    {
      "issue_id":     "REV-0042-001",
      "dimension":    "AMBIGUITY",
      "severity":     "blocking",          // blocking | non-blocking
      "location":     "Scope section, paragraph 2",
      "description":  "\"real-time updates\" is ambiguous. Does this mean WebSocket push, server-sent events, or polling under 1 second? The Architecture Agent cannot make this decision.",
      "suggested_fix": "Specify the exact delivery mechanism and acceptable latency for updates."
    },
    {
      "issue_id":     "REV-0042-002",
      "dimension":    "TESTABILITY",
      "severity":     "non-blocking",
      "location":     "Performance section",
      "description":  "\"The system should be responsive\" has no measurable threshold.",
      "suggested_fix": "Replace with a specific latency target, e.g. p95 under 300ms."
    }
  ],

  "revision_tasks_created": ["TASK-0891", "TASK-0892"],
  "next_action":      "spec_generator_agent",
  "cycle_count":      1,
  "max_cycles":       3,
  "model":            "claude-sonnet-4-5-api",
  "tokens_used":      847,
  "cost_usd":         0.006
}

Human Escalation #escalation

When cycle_count reaches 3 and the artifact is still not approved, the task status moves to HUMAN_REVIEW_REQUIRED. The relevant stakeholder is notified with a summary package containing:

  • The current artifact (spec, architecture, tasks, test cases, or code)
  • All three review cycles — what was flagged each time and how the Producer responded
  • The specific issues still unresolved after 3 cycles
  • A recommended resolution from the Review Agent
Review AgentEscalates ToTypical Cause
Spec Review AgentProduct OwnerRequirement is genuinely ambiguous — PM must decide
Architecture Review AgentTech Lead / ArchitectCompeting valid architecture approaches — human judgement needed
Task Review AgentTech LeadTask scope cannot be resolved — architectural clarification needed
Test Case Review AgentQA LeadUntestable requirement — spec or architecture must change
Code Review AgentTech LeadCode pattern conflict — style guide or architecture decision needed

After human resolution, the human updates the relevant artifact or revision task directly in Jira. The pipeline resumes from the point of escalation — the Producer picks up the human-modified task and resubmits. The cycle_count resets to 0.
