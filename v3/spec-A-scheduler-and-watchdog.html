Specification A of F
Master Scheduler, Watchdog & State Store
The orchestration core — task lifecycle management, pipeline DAG execution, agent dispatch, cost enforcement, resiliency monitoring, and failure recovery.
Components: 01, 02, 03 Version: 1.0 Status: Draft May 2026

Overview #overview

The orchestration layer is the central nervous system of the FORGE platform. It consists of three tightly coupled components: the Master Scheduler, the Watchdog, and the Redis State Store. Together they are responsible for knowing what every agent is doing at every moment, ensuring work progresses through the pipeline correctly, recovering from any failure automatically, and enforcing all cost and retry limits.

No agent acts without instruction from the Master Scheduler. No status changes in Jira without the Scheduler or an authorized agent making that change. No failure goes undetected for more than 3 minutes. The orchestration layer is the single point of authority over all task state in the platform.

Design Principle
The Master Scheduler is the only component with global write access to task state. All agents report their results to the Scheduler, which then decides the next action. Agents never directly trigger other agents.

Master Scheduler #master-scheduler

The Master Scheduler is a long-running Python process. It runs continuously and is the first process started when the platform boots. It maintains the complete state of every active task across all developers and all tenants. It reads from the Redis State Store and writes to both Redis and Jira via the Jira Integration Layer.

State Machine #state-machine

Every task ticket has a status. The Scheduler owns all status transitions. The valid transitions are defined below. Any transition not listed here is illegal — the Scheduler will reject it and log an anomaly.

CREATED
  └─► QUEUED                    (dependencies satisfied)

QUEUED
  └─► IN PROGRESS               (Code Agent dequeues)

IN PROGRESS
  └─► CODE COMPLETE             (Code Agent reports files committed)

CODE COMPLETE
  └─► SECURITY SCAN IN PROGRESS (Scheduler dispatches Security Agent)

SECURITY SCAN IN PROGRESS
  ├─► TESTING IN PROGRESS       (no Critical/High findings)
  └─► QUEUED                    (Critical/High found — fix first)

TESTING IN PROGRESS
  ├─► PERFORMANCE TESTING       (all tests pass, coverage met)
  └─► BUILD FAILING             (any test fails or coverage short)

BUILD FAILING
  └─► QUEUED                    (all linked bugs closed)

PERFORMANCE TESTING IN PROGRESS
  ├─► COMPLETED                 (all metrics within threshold)
  └─► PERFORMANCE FAILING       (any metric outside threshold)

PERFORMANCE FAILING
  └─► QUEUED                    (all linked bugs closed)

COMPLETED WITH ERRORS
  └─► COMPLETED                 (all follow-on bugs closed)

Any status
  └─► SUSPENDED                 (suspension condition met)

SUSPENDED
  └─► QUEUED                    (human manually resets)

DAG Execution #dag-execution

The Scheduler maintains a Directed Acyclic Graph (DAG) of all tasks within a tenant. Each node is a task. Each directed edge represents a dependency — the source task must reach COMPLETED status before the target task can advance from CREATED to QUEUED.

The DAG is rebuilt every 30 seconds by reading all active Jira dependency links. If a user changes a dependency in Jira, the Scheduler picks it up on the next rebuild cycle. The Scheduler does not cache dependency state beyond one cycle.

Parallelism: The Scheduler identifies all tasks with no unresolved dependencies and dispatches them simultaneously to available developer droplets. Tasks that share a file lock (detected by the Conflict Detector) are serialized automatically — the Conflict Detector holds the lower-priority task in QUEUED until the file lock is released.

Cycle detection: On every DAG rebuild, the Scheduler runs a depth-first search to detect cycles. If a cycle is found, all tasks in the cycle are moved to SUSPENDED with a comment in Jira identifying the circular dependency. Human intervention is required to break the cycle.

Task Dispatch #task-dispatch

When a task is ready to advance, the Scheduler does not call the agent directly. It places the task descriptor on the agent's work queue (a Redis list). The agent polls its queue, dequeues the task, processes it, and writes its result back to a Redis result queue. The Scheduler reads from the result queue on a 5-second polling interval.

This queue-based dispatch means the Scheduler is never blocked waiting for an agent. It places work and moves on. If an agent is slow or unavailable, the Watchdog detects it via the heartbeat system — not by the Scheduler timing out on a direct call.

Cost Enforcement #cost-enforcement

The Scheduler is the sole enforcer of all cost limits. Before dispatching any agent task that involves an LLM API call, the Scheduler checks the current spend against all applicable caps. If any cap would be breached by the next call, the Scheduler does not dispatch the task. It pauses the pipeline, writes a comment to the Jira ticket, and sends an alert notification to the operator.

CapDefaultScopeOn Breach
Daily spend cap$5.00Per developerPause all that developer's tasks until midnight UTC
Monthly spend cap$50.00Per developerPause all tasks until next billing cycle, alert operator
Tenant daily cap$500.00Per tenantPause all tenant tasks, immediate operator alert
Per-call token budgetVaries by agentPer API callHard max_tokens enforced in API call — cannot be exceeded

Every LLM API call response is read by the Scheduler immediately. Input and output token counts are extracted from the response metadata and added to the running spend tracker in Redis. The spend tracker is updated atomically — there is no window where a burst of calls can collectively exceed the cap before the tracker catches up.

Human Escalation #escalation

The Scheduler escalates to a human in exactly four situations. In all other situations it resolves the issue autonomously.

Escalation TriggerAction Taken
Code failure retry count reaches 3Task moved to SUSPENDED. Jira comment with full failure history. Operator notified.
Resiliency retry count reaches 3Task moved to SUSPENDED. Jira comment with infrastructure failure history. Operator notified.
Daily or monthly budget cap breachedAll affected tasks paused. Operator notified with current spend breakdown.
Requirement ambiguity detected by Spec GeneratorPipeline does not start. Product owner notified with one specific clarifying question.
Non-Negotiable
The Scheduler never guesses when a situation is ambiguous. It never merges its own code to main. It never deploys to production without explicit human approval. These three behaviors are hardcoded and cannot be overridden by configuration.

MASTER_CONTEXT.md #master-context

MASTER_CONTEXT.md is a structured markdown file maintained per active task. It is the recovery document — when a fresh agent picks up a requeued task after a crash, it reads this file first and continues from the last checkpoint rather than starting from the beginning.

Written by: Every agent writes to it after every meaningful unit of progress. The Code Agent writes after every file. The Build Agent writes after build completion. The Test Agent writes after the test run. All writes go through the Scheduler to prevent concurrent write conflicts.

Maximum size: 3,000 tokens, enforced on every write. When a write would exceed this limit, the Scheduler prunes the oldest entries, keeping the most recent progress state, all file completion records, and all key decisions.

Watchdog #watchdog

The Watchdog is a subprocess of the Master Scheduler. It runs in a dedicated thread and operates independently of the main dispatch loop. Its sole responsibility is detecting when something has gone wrong and triggering the appropriate recovery action. It never dispatches agents directly — it signals the Scheduler, which handles dispatch.

Heartbeat System #heartbeat

Every agent emits a heartbeat to the Redis State Store every 30 seconds while it is working on a task. The heartbeat is a lightweight JSON write to a Redis key with a 90-second TTL. If the key expires without being refreshed, the agent has gone silent.

Status-Specific Timeout Thresholds #timeouts

Different pipeline stages have legitimately different durations. The Watchdog uses per-status thresholds rather than a single global timeout, so it does not falsely flag a legitimately long security scan as a hung agent.

Task StatusExpected DurationTimeout ThresholdExtended Timeout (once)
IN PROGRESS — code generation2–15 min30 min45 min
IN PROGRESS — bug fix2–15 min30 min45 min
CODE COMPLETE — awaiting build<2 min10 min—
SECURITY SCAN IN PROGRESS3–10 min20 min30 min
TESTING IN PROGRESS2–10 min20 min30 min
VERIFYING — bug re-check2–10 min20 min—
PERFORMANCE TESTING IN PROGRESS5–20 min45 min60 min
FIX COMPLETE — awaiting verify<2 min10 min—

When a task reaches its timeout threshold and the agent appears to be making some progress (heartbeat present, progress note changing slowly), the Watchdog extends the timeout once by 50% before triggering recovery. This handles legitimately slow operations such as large file generation or a slow compiler. After the extended timeout expires, recovery is triggered regardless.

Recovery Scenarios #scenarios

Scenario 1 — Agent Crashed #scenario-crash

The agent process terminated. Heartbeat key expired in Redis. The task is stuck in a mid-pipeline status with no agent working it.

  1. Watchdog signals Scheduler: agent {agent_id} is silent, task {task_id} needs recovery.
  2. Scheduler checks the git feature branch for committed work.
  3. If no commits exist: Move task to QUEUED. Increment resiliency retry counter. Add Jira comment. Spin up fresh agent instance on same droplet.
  4. If partial commits exist: Roll back the branch to the last clean commit recorded in MASTER_CONTEXT.md. Move task to QUEUED. Increment resiliency retry counter. Add Jira comment. Spin up fresh agent.
  5. If all files are committed: Advance task to the next stage normally. No retry counter increment — the agent completed its work before crashing.
Jira Comment Template — Agent Crash
"FORGE Bot: Code Agent (dev-042) became unresponsive at 14:47 UTC. 2 of 6 files were committed before failure. Partial work rolled back to commit a3f92bc. Task requeued for attempt 2 of 3. Recovery triggered automatically."

Scenario 2 — GPU Droplet Down #scenario-droplet

The droplet is unreachable. Health ping fails for 2 consecutive Watchdog cycles (2 minutes). Any work in memory is lost. Work committed to git may still be intact.

  1. Watchdog signals Scheduler: droplet {droplet_id} unreachable for developer {developer_id}.
  2. Scheduler checks git branch for committed work (same evaluation as Scenario 1).
  3. Resource Controller attempts droplet restart via cloud API. Waits 3 minutes for restart.
  4. If restart succeeds: Requeue task on the restarted droplet. Increment resiliency retry counter.
  5. If restart fails: Multi-Cloud Provisioner provisions a replacement on the next cheapest available cloud. Requeue task on the new droplet. Increment resiliency retry counter.
  6. Add Jira comment with droplet ID, cloud provider, failure detail, and recovery action taken.

Scenario 3 — Agent Hung #scenario-hung

The agent is alive. The droplet is reachable. The heartbeat is present. But the progress_note field has not changed for 2× the expected duration — the agent is not making progress despite being alive.

  1. Watchdog signals Scheduler: agent {agent_id} appears hung on task {task_id}.
  2. Scheduler sends SIGTERM to the agent process. Waits 30 seconds for graceful shutdown.
  3. If agent does not shut down cleanly within 30 seconds: send SIGKILL.
  4. Evaluate committed work on git branch (same as Scenario 1).
  5. Requeue task. Increment resiliency retry counter. Spin up fresh agent instance.

Scenario 4 — Jira Sync Inconsistency #scenario-jira

The internal Redis state and the Jira ticket status disagree for more than 10 minutes. This can happen after a Jira API outage, network partition, or failed write.

  1. Watchdog detects mismatch: Redis says CODE_COMPLETE, Jira says IN_PROGRESS.
  2. Jira Integration Layer attempts re-sync: write the Redis state to Jira.
  3. If re-sync succeeds within 3 attempts: continue pipeline normally. Log the inconsistency for audit.
  4. If re-sync fails 3 times: operator is alerted. Pipeline continues using Redis as the source of truth. Jira is updated when connectivity is restored. The discrepancy is logged and included in the next operator report.

Retry Counter Separation #retry-counters

Every task and bug ticket carries two independent retry counters. They never share a budget.

CounterIncremented ByDefault MaxTracks
code_failure_retriesScheduler when Code Agent fix attempt fails test/security/perf re-check3Build errors, test failures, security findings, performance regressions
resiliency_retriesWatchdog on every infrastructure recovery event3Agent crashes, droplet failures, hung agents

A task is moved to SUSPENDED only when either counter reaches its maximum. A task that suffers two infrastructure failures and then has one code failure still has two code failure retries remaining. An infrastructure failure does not consume the code failure budget, and vice versa.

Example
Task FORGE-291: agent crashes twice (resiliency_retries = 2), then a test fails (code_failure_retries = 1), then another crash (resiliency_retries = 3 → SUSPENDED). The code failure budget of 3 was never exhausted — but the resiliency budget was. Human intervention resolves the infrastructure issue, resets resiliency_retries to 0, and the task resumes with code_failure_retries still at 1.

State Store (Redis) #state-store

The Redis State Store is the authoritative internal source of truth for all runtime state. It is not a cache of Jira — it is the primary state store. Jira is the external representation. Redis is kept in sync with Jira by the Jira Integration Layer, with Redis always winning on conflict.

Redis is chosen for the state store because it supports: atomic operations (preventing race conditions on counter increments), key expiry (used for heartbeat TTL), list structures (used for agent work queues), and pub/sub (used for Watchdog event notifications). It handles 100,000+ writes per second — the heartbeat volume of 100 active agents is not a load concern.

Jira Sync #sync

The Jira Integration Layer maintains a background sync loop that runs every 60 seconds. It compares the status of every active task in Redis against the corresponding Jira ticket status. Any discrepancy triggers an immediate re-sync write to Jira. Sync failures are retried up to 3 times with exponential backoff (1s, 2s, 4s). After 3 failures the discrepancy is logged and the operator is notified on the next heartbeat report.

Writes to Jira are batched where possible to stay within Jira's API rate limits. The Integration Layer maintains a write queue with a maximum of 10 writes per second per tenant. Status changes are prioritized over comment writes in the queue. Comment writes are coalesced — if multiple comments are queued for the same ticket, they are combined into a single API call.

JSON Interfaces #interfaces

All data structures crossing component boundaries are defined here. These schemas are the contract between the Scheduler and all agents. Any agent returning a payload that does not validate against its schema causes the Scheduler to log a schema violation, move the task to SUSPENDED, and alert the operator.
