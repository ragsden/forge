Multi-Tenant Architecture & Operations
How FORGE operates at scale with 100 concurrent developers per tenant — isolation boundaries, dependency resolution, conflict prevention, PR orchestration, the developer dashboard, SOC 2 controls, and customer onboarding.
Components: 24–28 Version: 1.0 Status: Draft May 2026

Overview #overview

The multi-tenant layer is what makes FORGE viable for real engineering teams rather than solo projects. At scale — 100 developers, hundreds of concurrent tasks, thousands of files changing simultaneously — coordination problems that are invisible at small scale become existential. Two developers modifying the same file, a feature that depends on another that hasn't been built yet, a PR merge that breaks another developer's branch: these are daily realities in any active engineering team.

FORGE handles all of these automatically. The Feature Dependency DAG Resolver determines what can run in parallel and what must wait. The Conflict Detector prevents two agents from ever writing to the same file simultaneously. The PR Merge Orchestrator sequences merges to keep the main branch stable. The Developer Dashboard gives the team full visibility into everything happening at once.

Design Goal
A 100-developer team using FORGE should require fewer coordination meetings than a 10-developer team without it. Dependency ordering, conflict prevention, and merge sequencing are automated. The team focuses on requirements and review — not on who is working on what and in what order.

Isolation Architecture #isolation

Tenant-Level Isolation #tenant-isolation

Every customer organization is a completely isolated tenant. The following resources are never shared between tenants under any circumstances:

Data
Source code, git history, training examples, task descriptors, audit logs. Stored in tenant-namespaced object storage buckets. Cross-tenant access is architecturally impossible — no shared database tables, no shared object storage prefixes.
Models
LoRA adapter files. Each tenant's adapter is stored in their namespaced model registry. The base model weights are shared (they are not customer data), but adapters are exclusively per-tenant. A tenant's codebase knowledge never influences another tenant's model.
Compute
GPU droplets. Developer droplets are assigned to specific tenants and developers. No tenant's work runs on another tenant's droplet. Shared orchestration infrastructure (Redis, Scheduler) is namespace-partitioned with tenant_id as a mandatory key prefix.
Network
VPC isolation (Enterprise tier). Each tenant's compute resources run inside a dedicated VPC. No inter-tenant network routes exist. Standard tier tenants run in shared VPCs with network-level security group isolation between tenant namespaces.
Credentials
API keys, Jira tokens, cloud credentials, signing keys. Stored in a secrets manager with tenant-namespaced access policies. No service account has access to credentials outside its assigned tenant namespace.

Developer-Level Isolation #developer-isolation

Within a tenant, each developer's pipeline is isolated from every other developer's pipeline. This isolation prevents one developer's failing task from affecting another developer's work in any way.

Isolation Boundaries at 100 Developers #isolation-boundaries

At 100 developers running concurrent pipelines, the following isolation boundaries are enforced simultaneously:

  • 100 dedicated GPU droplets, each with its own IP and network namespace
  • 100 independent git branch namespaces — no developer's Code Agent can commit to another developer's branch
  • 100 independent Docker environments — a crashing container in one developer's pipeline does not affect any other
  • 200+ active Redis queue keys (code + result queues per developer) — Scheduler reads only the queues it owns
  • File lock registry in Redis prevents any two developers from acquiring a lock on the same file simultaneously
  • DAG resolver runs per tenant — all 100 developers' tasks are resolved in a single DAG, but execution is still isolated per developer

Feature Dependency DAG Resolver #dag-resolver

The Feature Dependency DAG Resolver constructs and maintains a Directed Acyclic Graph of all tasks within a tenant. It is the component that transforms a flat list of Jira tickets into an ordered execution plan — determining what can run in parallel, what must wait, and what is blocked by a cycle.

DAG Construction #dag-construction

The DAG is rebuilt every 30 seconds by the Master Scheduler. Each rebuild reads all active Jira dependency links for the tenant and constructs a fresh graph. The rebuild is not incremental — it starts from scratch each cycle. This ensures that any user edit to a dependency link in Jira is picked up within 30 seconds without requiring any explicit notification to the platform.

DAG construction algorithm:

1. Fetch all active task tickets for tenant via Jira API
   (status not in [COMPLETED, SUSPENDED])

2. For each ticket: read "is blocked by" links → these are
   incoming dependency edges for this node

3. Build adjacency list:
   graph = {task_id: [dependency_task_ids]}

4. Run cycle detection (DFS)
   If cycle found: mark all cycle members as SUSPENDED
   Post Jira comment identifying the circular dependency

5. Compute topological sort → execution order
   Tasks with no unmet dependencies → ELIGIBLE set

6. For each task in ELIGIBLE set:
   Check file lock conflicts (see Conflict Detector)
   If no conflict: advance from CREATED to QUEUED
   If conflict: hold in CREATED, re-check next cycle

7. Write serialized DAG to Redis: dag:{tenant_id}
   Expires in 60 seconds — always rebuilt before expiry

Parallelism Extraction #dag-parallelism

The DAG resolver identifies all tasks that have no unresolved dependencies and no file lock conflicts, and queues them simultaneously. This is the primary mechanism for parallel execution. At 100 developers with 200+ tasks in flight, large portions of the DAG are typically runnable in parallel — particularly in the early phases of a large feature set where foundation tasks have already completed.

In this example, a naive sequential execution would take 8 task durations. With DAG-aware parallel execution it takes 4 task durations — a 50% reduction in calendar time. In practice, real feature sets show 20–40% time savings from parallelism depending on how interconnected the dependency graph is.

Cycle Detection #dag-cycle-detection

A cycle in the dependency graph means two or more tasks each depend on each other — a situation where no task can ever start because each is waiting for the other. The DAG resolver runs depth-first search on every rebuild cycle. If a cycle is detected:

  1. All tasks in the cycle are identified by traversing the cycle path.
  2. All tasks in the cycle are moved to SUSPENDED status.
  3. A Jira comment is posted on each affected ticket identifying: the cycle members, the specific dependency link that creates the cycle, and the instruction to remove one of the links to break the cycle.
  4. No pipeline work proceeds on any cycle member until a human resolves the dependency conflict.
  5. The alert is also surfaced on the Developer Dashboard as a blocking anomaly.

User Editing of the DAG #dag-user-editing

The product owner or any developer can modify the dependency graph at any time by editing the Jira dependency links directly in Jira. The platform picks up all changes within 30 seconds on the next DAG rebuild cycle. No notification to FORGE is required — the platform reads Jira as the source of truth for dependencies on every cycle.

Mid-Execution Edits
If a task is currently IN PROGRESS and a dependency is added to it that is not yet complete, the platform does not interrupt the running task. The dependency constraint applies to the next pipeline stage — if the task reaches CODE COMPLETE, it will not advance to SECURITY SCAN IN PROGRESS until the newly added dependency is satisfied. Active work is never interrupted by dependency changes.

Conflict Detector #conflict-detector

The Conflict Detector prevents merge conflicts before they occur. It does this by maintaining a file lock registry — a set of file paths that are currently being written by an active task. No two tasks can hold a lock on the same file simultaneously. By enforcing this at the QUEUED-to-IN PROGRESS transition, the platform ensures that two Code Agents never write to the same file at the same time.

File Lock Registry #file-locks

The file lock registry is implemented as a set of Redis keys. Each lock key stores the task ID currently holding the lock. Lock acquisition is atomic — it uses a Redis SET NX (set if not exists) operation, which is guaranteed to succeed for only one caller even under concurrent requests.

Lock key format:  lock:file:{sha256(file_path)}
Lock value:       {task_id}:{developer_id}:{acquired_at_iso}
Lock TTL:         None — locks are released explicitly on PR merge

// Acquisition (atomic):
result = redis.SET(
    f"lock:file:{sha256(file_path)}",
    f"{task_id}:{developer_id}:{now_iso}",
    nx=True  // only set if key does not exist
)
// result = True  → lock acquired
// result = None  → lock held by another task — conflict

// Release (on PR merge event from git webhook):
redis.DELETE(f"lock:file:{sha256(file_path)}")

Lock acquisition happens before a task advances from CREATED to QUEUED. If any file in the task's files_to_write list is already locked, the task remains in CREATED and is re-checked on the next DAG rebuild cycle. The task does not fail — it waits. When the holding task's PR is merged and its locks are released, the waiting task advances to QUEUED automatically on the next cycle.

Resolution Strategies #conflict-resolution

When a lock conflict is detected, the platform applies one of three resolution strategies based on the tasks' relationship:

ScenarioStrategyOutcome
Neither task depends on the otherPriority-based serialization. Higher priority task runs first. Lower priority task waits.Lower priority task always gets the updated file — cleaner than the alternative.
Task B depends on Task A (via Jira link)Dependency ordering. Task A runs first regardless of priority.Task B naturally runs after Task A by DAG resolution — lock conflict is a symptom of a missing dependency link that the Spec Generator should have caught.
Tasks have equal priority and no dependencyFirst-come-first-served by lock acquisition timestamp.The task that acquired the lock first runs. The other waits.

In all cases, FORGE Bot posts a comment on the waiting task: "This task is waiting for FORGE-291 to complete and merge before it can start. The file src/payments/stripe_client.rs is currently locked by that task. Estimated wait: 15–30 minutes."

PR Merge Orchestrator #pr-orchestrator

The PR Merge Orchestrator manages the sequence in which open pull requests are merged to the main branch. With 100 developers generating PRs concurrently, uncoordinated merges would regularly produce a broken main branch — a developer merges their PR, breaking the tests for another PR that was passing moments before.

Merge Sequencing #pr-sequence

The Orchestrator maintains a merge queue — an ordered list of PRs that have been approved by a human reviewer and are ready to merge. PRs enter the queue when they receive the required approvals. They are dequeued and merged one at a time, in priority order.

Priority ordering for the merge queue:

  1. Bug fix PRs with P1 severity — highest priority, merged immediately
  2. Security fix PRs — merged before feature PRs regardless of order
  3. Feature PRs that are blocking other queued tasks (have dependents waiting)
  4. Feature PRs by task priority (inherited from Jira task priority field)
  5. Feature PRs by PR creation timestamp — first approved, first merged

Only one PR is merged at a time. While a merge is in progress (typically 30–60 seconds including CI run on main), no other PR is dequeued. This prevents the race condition where two PRs are simultaneously merged and the combined change breaks something neither PR broke independently.

Rebase Strategy #pr-rebase

Before merging any PR, the Orchestrator rebases the feature branch onto the current tip of main. This ensures the PR always incorporates the latest changes from main — including any changes from PRs merged earlier in the queue.

Merge sequence for PR FORGE-291:

1. Dequeue FORGE-291 from merge queue
2. Fetch current main branch tip: commit abc1234
3. Rebase feature/FORGE-291-stripe-retry onto abc1234
   - If rebase succeeds cleanly: continue
   - If rebase conflict:
       a. Post Jira comment: "Rebase conflict detected.
          Human resolution required before this PR can merge."
       b. Move PR to back of merge queue
       c. Move next PR to front and continue
4. Run CI on rebased branch (fast — typically 2–5 min)
5. If CI passes: merge to main (fast-forward merge)
6. Delete feature branch
7. Release all file locks held by this task
8. Post Jira comment: "Merged to main as commit xyz9876."
9. Update Jira task to COMPLETED (if all bugs also closed)
10. Dequeue next PR and repeat

In practice, rebase conflicts are rare because the Conflict Detector prevents two tasks from writing to the same file simultaneously. A rebase conflict can still occur if a task modifies a file that another task's test file references — a scenario the Conflict Detector does not catch because test files are not in the task's files_to_write list for the conflicting task. When it does occur, a human developer resolves the conflict, re-pushes the branch, and the PR re-enters the merge queue.

Scaling Beyond 100 Developers #beyond-100

The platform is designed to scale beyond 100 developers per tenant with the following architectural changes that do not require re-engineering any existing component:

  • Master Scheduler sharding: At 200+ developers, the Scheduler is sharded by developer_id hash — each Scheduler instance owns a subset of developers. The DAG resolver runs on a dedicated process reading from all shards.
  • Redis clustering: Standard Redis Cluster with hash-slot partitioning handles millions of keys. The key design (all keys namespaced with tenant_id and developer_id) is already cluster-compatible.
  • Jira API rate limits: At 200+ developers, Jira's API rate limits become a bottleneck. Solution: batch all reads into bulk queries, use Jira webhooks to receive push notifications rather than polling, and cache ticket state in Redis with webhook-triggered invalidation.
  • DAG rebuild time: At 500+ tasks per tenant, DAG rebuild may take 5–10 seconds. Solution: incremental DAG updates triggered by webhook events rather than full rebuild every 30 seconds.

SOC 2 Controls #soc2

Data Residency #data-residency

Enterprise customers can configure data residency constraints that restrict all their compute and storage to a specific geographic region. When data residency is configured:

  • All GPU droplets for that tenant are provisioned only in cloud regions within the configured geography
  • The Multi-Cloud Provisioner's selection algorithm excludes any region outside the residency boundary (see Spec D §selection-algorithm)
  • All object storage buckets (source code, training data, model adapters, audit logs) are created in compliant regions only
  • The Claude API fallback is disabled for tenants with strict data residency requirements — all inference must run on self-hosted infrastructure within the boundary
  • Jira integration is unaffected — Jira is the customer's own system and is not subject to FORGE's data residency controls

Supported residency zones at launch: EU (GDPR compliance), US (FedRAMP aligned), AU (Australia), UK (post-Brexit). Additional zones added on customer request with a 6-week lead time for infrastructure provisioning.

Customer Onboarding #onboarding

Onboarding a new customer organization takes approximately 2 hours of wall clock time, most of which is automated. Human effort from the customer: approximately 30 minutes to provide credentials and approve the initial spec. Human effort from FORGE: zero — the onboarding sequence is fully scripted.

T+0 — Account creation
Tenant provisioned, credentials collected
Customer signs up. FORGE creates the tenant namespace, provisions the secrets manager with a blank tenant vault, creates the Jira project and FORGE Bot service account, and sends the customer a credential collection form. Customer fills in: git repository access token, Jira admin credentials, cloud account details (optional for Standard tier), and their preferred data residency region.
T+15 min — Ingestion begins
Codebase ingestion and initial knowledge scan
Ingestion Agent clones all configured repositories. Reads full git history. Extracts all training examples. Quality-scores each example. Writes approved examples to the tenant's training store. Generates a summary report: number of examples by source type, quality distribution, estimated training dataset size.
T+45 min — Initial training
First LoRA adapter trained
LoRA Training Orchestrator starts the initial training run on a provisioned H100. Takes 3–5 hours for a typical codebase. While training runs, the customer can begin using the platform with the generic base model — the adapter replaces it automatically when ready.
T+60 min — Developer droplets provisioned
One droplet per developer, powered off
Resource Controller provisions one GPU droplet per developer account (powered off, no billing). Each droplet gets the base model weights pre-loaded to disk so the first boot is fast. Developer dashboard activated and shared with the tech lead.
T+90 min — First task submission
Customer submits first requirement
Product owner submits a one-line requirement to the Functional Spec Generator. The conversation runs, the spec is approved, tickets are created in Jira. The pipeline begins. Customer sees their first FORGE task moving through Jira statuses within minutes.
T+4–5 hours — Fine-tuned model live
Company adapter promoted to production
Initial training run completes. LLM-as-Judge validates the adapter quality vs. the generic base model. If quality is equal or better (it always is — any codebase data improves on the generic model), the adapter is promoted to production. All subsequent Code Agent calls use the company-specific model. Context windows begin shrinking immediately.

After onboarding, the customer receives a Welcome Report containing: the number of training examples extracted from their codebase, the initial PR approval rate benchmark, estimated context window reduction by month 6, the cost projection for their team size, and the link to their developer dashboard.
