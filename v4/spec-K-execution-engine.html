Specification K — V4 · Core
Execution Engine
When the user selects an option and clicks Execute, the Execution Engine assembles the exact agents needed, runs each with its review agent, handles mixed execution levels within a single plan, and assembles all outputs into a final deliverable artifact.
V4 CoreVersion: 4.0Status: DraftMay 2026

Overview #overview

Core Principle
Automate everything possible. Every task in a plan is pushed to the highest achievable execution level. Level 3 tasks complete without user involvement. Level 2 tasks present a single confirmation step. Level 1 tasks produce a complete document. The user never does research, never fills forms from scratch, never searches manually — the platform does all of it and presents the result.
User clicks "Execute Option A" ↓ Execution Engine reads the selected option's task graph ↓ For each task in dependency order: Spin up the appropriate agent (with Master Plan Creator's generated prompt) Agent produces its output Review Agent evaluates (up to 3 cycles) Output stored in plan store ↓ Deliverable Assembly Agent combines all outputs ↓ Delivery Review Agent checks completeness ↓ Final artifact presented to user

User Selects an Option #user-selects

The options are presented as a rich visual artifact — a webpage or interactive card interface — before any execution begins. Each option shows: the strategic thesis, expected outcome, cash cost, points/effort required, timeline, and a breakdown of what the platform will do vs what the user needs to do.

The user reads the options and clicks Execute on one. This is the last decision the user makes until the platform either completes the plan or surfaces a Level 2 confirmation step. The platform runs autonomously from this point forward.

The user can also modify the plan before executing — adding constraints, swapping tasks between options, or changing the execution level of specific tasks (e.g. downgrading a Level 3 booking to Level 2 if they want to confirm before the flight is booked).

Dynamic Agent Assembly #agent-assembly

The Execution Engine reads the task graph from the selected option and instantiates the required agents. Each agent is a general-purpose execution agent given a specific system prompt generated by the Master Plan Creator. The same underlying infrastructure runs a Travel Research Agent, a Business Plan Agent, and a Code Agent — what differs is the prompt, the tools available, and the execution level.

Agent typeUnderlying capabilityTools providedPrompt source
Research AgentsWeb search + document synthesisweb_search, web_fetch, document_createMaster Plan Creator generated
Booking AgentsAPI calls to travel/booking systemsflight_api, hotel_api, payment_apiMaster Plan Creator generated
Document AgentsLLM document generationdocument_create, spreadsheet_createMaster Plan Creator generated

Financial AgentsCalculation + API data retrievalfinancial_api, calculator, document_createMaster Plan Creator generated
Form AgentsWeb automation + form fillingbrowser_automation, form_fillMaster Plan Creator generated

Tasks with no dependencies start immediately in parallel. Tasks with dependencies wait for their prerequisite tasks to complete and pass review. The dependency graph from the Master Plan Creator drives the execution order — exactly as the V3 DAG drove code task execution.

Level 3 — Fully Autonomous #level3

LEVEL 3
Platform executes completely. User sees the result.

Level 3 tasks are executed by the platform using real APIs, stored credentials, and web automation. The user is not involved during execution. They see the completed result — a booking confirmation, a committed code change, a created document — when the task finishes.

Examples: Search flight availability via Skyscanner API · Book a hotel using stored credit card · Commit code to customer GitHub branch · Create a financial model spreadsheet · Generate a day-by-day itinerary document · Search for award availability across airline partner programs

Required infrastructure: Secure credential vault (user provides API keys and card details once, platform uses them) · Web automation for sites without APIs · Result verification (platform confirms the action completed successfully)

Guardrails: Spending limits enforced (user sets maximum per transaction) · Irreversible actions flagged before execution · Full audit log of every action taken

Level 2 — One-Click Execute #level2

LEVEL 2
Platform prepares everything. User confirms with one click.

Level 2 tasks are those where the platform can prepare everything but the final action requires explicit human authority — because it involves a legal commitment, a financial transaction above a guardrail threshold, or a decision that cannot be reversed.

What the platform delivers: A fully prepared artifact with every field populated, every decision made, every option researched — and a single prominent "Confirm and Submit" button. The human reads what will happen and clicks once.

Examples:

  • Credit card application — platform fills every field from user profile, user reviews and submits
  • Points transfer — platform calculates optimal transfer amount and partner, user confirms the irreversible transfer
  • Legal document — platform drafts the complete document, user reviews and signs
  • Large purchase above spending limit — platform stages the booking, user approves the charge
  • Job offer response — platform drafts the negotiation email, user reads and sends

The key principle: Level 2 is not "the platform couldn't finish." It is "the platform finished everything except the act that requires your authority." The human contribution is review + approval, not research or preparation.

Level 1 — Advise and Deliver #level1

LEVEL 1
Platform researches and delivers a complete document. Human acts on it.

Level 1 tasks are those where the output is a document, recommendation, or analysis — not an action. The platform cannot execute the action itself (it requires physical presence, specialized professional judgment, or information only the human can provide). But it delivers everything the human needs to act quickly and confidently.

Examples: Regulatory requirements for opening a dental practice in California · Peanut allergy meal policy on Air Tahiti Nui · Salary range for a senior engineer in Austin · Best neighborhoods for a retail dental practice · SAT study schedule for a student with 12 weeks and 15 hours/week available

What makes a good Level 1 output: Specific, not generic. Personalized to the user's situation. Actionable — tells the user exactly what to do, not just what to consider. Comprehensive enough that the human doesn't need to do additional research.

Review Loop per Agent #review-loop

Every producer agent in the execution graph has a review agent. The review agent and its rubric were generated by the Master Plan Creator when it built the plan. The same universal review loop from V3 applies: up to 3 revision cycles, then human escalation.

For Level 3 agents — review happens before the action is committed. The Review Agent checks the plan for the action (e.g. "book this specific flight on this date for this price") before the booking API is called. This prevents incorrect bookings.

For Level 2 agents — review happens before the artifact is presented to the user. The Review Agent checks the pre-filled form, document, or staged transaction for accuracy and completeness before the user sees the "Confirm" button.

For Level 1 agents — review checks the document for accuracy, completeness, and personalization before it is delivered to the user.

Deliverable Assembly Agent #deliverable

When all tasks in the plan are complete, the Deliverable Assembly Agent combines all outputs into the final deliverable package. What this looks like depends on the domain:

Business formationBusiness plan document setExecutive summary, market analysis, financial model (spreadsheet), regulatory checklist, location shortlist, hiring roadmap

Output Artifact #output-artifact

The final output of every V4 plan is a persistent personal artifact — a webpage hosted by the platform that the user can bookmark, share, and return to. It is not a PDF or a Word document. It is a living artifact that updates as actions complete and can serve as the source of truth for the entire plan.

For the Tahiti vacation, the artifact is a personal trip page that shows: confirmed flights (with PNR), confirmed hotel (with reservation number), day-by-day itinerary, dining reservations (if Level 3 booking was available), the allergy policy document, and a pre-trip checklist. The page updates in real time as each task completes.

The user can share the artifact (e.g. share the trip page with their travel partner), export it as a PDF, or keep it private. The platform retains it in the user profile for future reference.

Resource Management #resource

The Resource Manager in V4 works the same way as V3 — GPU on-demand per agent, torn down immediately when done — but the model selection is more nuanced because agents span more diverse task types:

Task typeModelHardwareRationale
Intake conversationClaude Sonnet APICPU / APIConversational, empathetic, fast
Master Plan creationClaude Opus APICPU / APIComplex multi-domain reasoning
Plan ReviewClaude Sonnet APICPU / APIReview and critique
Research agentsClaude Sonnet API + toolsCPU / APIWeb search + synthesis
Document generationClaude Sonnet APICPU / APILong-form writing
Code generationQwen2.5-Coder-32BL40S GPUV3 pipeline — specialist code model
Booking agentsClaude Haiku APICPU / APIStructured API calls, low reasoning needed
Financial modellingClaude Sonnet APICPU / APINumerical reasoning + document creation

Most V4 agents run on CPU with API calls — no GPU provisioning needed. GPU is only required when V4 routes a software goal through the V3 pipeline, which uses Qwen2.5-Coder-32B on L40S for code generation and Llama-3.1-70B on H100 for architecture design.

This means V4 plans are significantly cheaper per plan than V3 per software feature — because most domains do not require GPU inference. The cost model shifts from compute-heavy to API-call-heavy.
