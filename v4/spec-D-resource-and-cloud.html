Resource Controller & Multi-Cloud Provisioner
How FORGE manages GPU infrastructure — powering droplets on and off automatically, selecting the cheapest available cloud, and keeping GPU costs at 25–30% of always-on pricing.
Components: 15, 16, 17 Version: 1.0 Status: Draft May 2026

Overview #overview

The resource layer manages all GPU compute infrastructure for the platform. It consists of three components: the Resource Controller, which manages the on/off lifecycle of individual developer droplets; the Multi-Cloud Provisioner, which abstracts over multiple cloud providers and selects the cheapest available option; and the GPU Tier Manager, which maps task types to the appropriate hardware class.

The central design decision in this layer is that each developer gets a dedicated GPU droplet, not a slot in a shared pool. The Resource Controller powers that droplet on when work is queued and off when the developer is idle. This simplicity — 50 lines of on/off logic versus 500 lines of queue management for a shared pool — produces the same cost outcome at 25% utilization while providing complete isolation between developers and zero wait time for work to start.

Cost Impact
A developer working 6 hours per day on an L40S droplet at 25% active utilization costs $94/month. The same droplet running always-on costs $1,147/month. The Resource Controller delivers a 92% reduction in GPU spend for a typical developer workload.

Resource Controller #resource-controller

Dedicated Droplet Per Developer #dedicated-droplets

Every developer on the platform has one GPU droplet assigned to them. That droplet runs the Code Agent and the Build/Test agent executors for that developer's tasks. No other developer's work runs on it. The droplet's state — powered on or off — is managed entirely by the Resource Controller based on queue depth and activity signals.

The rationale for dedicated over shared is not primarily philosophical — it is engineering simplicity:

DimensionShared GPU PoolDedicated Droplet per Developer
Scheduler complexityQueue management, priority conflicts, resource starvation logic — ~500 linesOn/off lifecycle — ~50 lines
IsolationOne developer's memory-heavy model load can evict another'sComplete — no cross-developer interference
Wait timeTask waits for a free GPU slotZero — droplet is always exclusively available
DebuggingFailures may be caused by another tenant's workloadAll failures are attributable to one developer's work
Cost at 25% utilizationSame — shared pool at 25% utilization = dedicated at 25%Same — identical cost at equivalent utilization
Cost at 100% utilizationShared is cheaper — one GPU serves multiple light workloadsMore expensive — GPU idle between tasks

At real-world developer utilization patterns (25–35% active during working hours), dedicated droplets cost the same as a well-managed shared pool while being dramatically simpler to operate. The shared pool only wins at very high sustained utilization, which is not the profile of an interactive development workload.

Power-On Logic #power-on

The Resource Controller powers on a droplet when any of the following conditions are true:

  • A task enters QUEUED status on the developer's queue and the droplet is currently OFF
  • A bug ticket enters QUEUED status assigned to this developer and the droplet is OFF
  • The predictive pre-warm trigger fires (5 minutes before learned start time — see below)
  • The Watchdog signals that a replacement droplet is needed due to infrastructure failure

Power-on is a single DigitalOcean API call: POST /v2/droplets/{droplet_id}/actions with body {"type": "power_on"}. The Resource Controller then polls the droplet's status every 10 seconds until it responds to a health ping on port 8080. Boot time is typically 45–90 seconds. The task remains in QUEUED status during boot — it does not time out on the Watchdog until the per-status timeout threshold is reached (30 minutes for code generation tasks).

Boot Cost
Each power-on cycle costs approximately $0.118 in GPU time (90 seconds × $1.57/hr). The Resource Controller compares this against the Claude API cost for the queued task. If the task's token estimate is below the API routing threshold (500 tokens, approximately $0.001 in API cost), it is routed to the Claude API instead of booting the GPU — saving $0.117 per such task.

Power-Off and Idle Timeout #power-off

When the active work queue for a developer reaches zero depth — no QUEUED tasks, no QUEUED bugs — the Resource Controller starts an idle timer. When the timer expires, it powers off the droplet.

The idle timeout is adaptive, not fixed:

Pattern DetectedIdle Timeout AppliedRationale
Default (no pattern)15 minutesBalanced between cost and cold start wait
Burst pattern active (≥3 tasks in last 2 hours)30 minutesDeveloper is likely to submit another task soon — avoid repeated boot cycles
Post-burst (burst pattern just ended)5 minutesDeveloper has paused after a productive session — power off faster
Outside working hours (learned schedule)5 minutesNo activity expected — power off immediately to minimize waste
Pre-warm window activeInfinite — do not power offDroplet was pre-warmed for expected work — keep it on

Power-off is a single API call: POST /v2/droplets/{droplet_id}/actions with body {"type": "power_off"}. Billing stops within seconds of the power-off completing. The droplet is not destroyed — it is retained so it can be powered on again without provisioning time. The developer's disk, model weights in storage, and configuration are preserved between sessions.

Predictive Pre-Warming #prewarm

The Resource Controller learns each developer's working schedule from their activity history. It records the time of the first task submission each day for the past 30 days, computes a rolling average start time per day of the week, and pre-warms the droplet 5 minutes before that predicted start time.

Pre-warming means the developer never waits for a cold boot at the start of their workday. Their first task starts executing immediately.

// Example learned schedule for developer dev-042
{
  "developer_id": "dev-042",
  "learned_schedule": {
    "Monday":    "09:02 UTC",
    "Tuesday":   "08:58 UTC",
    "Wednesday": "09:05 UTC",
    "Thursday":  "09:00 UTC",
    "Friday":    "09:10 UTC",
    "Saturday":  null,
    "Sunday":    null
  },
  "prewarm_lead_time_min": 5,
  "confidence": 0.87,
  "sample_size_days": 28
}

// Pre-warm fires at 08:55 UTC Monday–Friday
// Droplet is ON and model is loaded by 09:00 UTC
// Developer's first task starts with zero wait

Pre-warming is suppressed if the developer's droplet is already on, if today is a recognized holiday (from a configurable holiday calendar per tenant's country), or if the confidence score is below 0.60 (insufficient data or highly irregular schedule).

API Routing for Small Tasks #api-routing

Not every task requires a GPU. When the Code Agent receives a task whose estimated token usage is below the configured threshold (default: 500 tokens), the Resource Controller compares the cost of booting the GPU against the cost of routing to the Claude API directly.

Decision logic:

  task_token_estimate = estimate_tokens(task_descriptor)

  if task_token_estimate < API_ROUTING_THRESHOLD:
    gpu_cost   = BOOT_COST_USD + (task_duration_est_sec / 3600) * GPU_RATE_USD
    api_cost   = task_token_estimate * CLAUDE_API_COST_PER_TOKEN
    
    if api_cost < gpu_cost:
      route to Claude API  // typically saves $0.10–0.12 per small task
    else:
      route to GPU

  else:
    route to GPU  // large tasks always use self-hosted model

// Example values:
//   API_ROUTING_THRESHOLD = 500 tokens
//   BOOT_COST_USD         = $0.118  (90 sec × $1.57/hr)
//   CLAUDE_API_COST       ≈ $0.001  (500 tokens at Sonnet pricing)
//   Decision:             route to API (saves $0.117)

Tasks routed to the Claude API use claude-haiku-4-5-20251001 for simple tasks (documentation, config generation, minor edits) and claude-sonnet-4-6 for anything requiring reasoning. The routing decision and cost comparison are logged per task for the developer dashboard.

Anomaly Detection #anomaly

The Resource Controller monitors for five anomaly conditions. When any is detected, the anomaly is logged, a dashboard alert is raised, and the operator is notified. Most anomalies are resolved automatically — operator intervention is only needed for persistent or unresolvable cases.

AnomalyDetection ConditionAutomatic Response
Stuck pipelineDroplet has been ON for more than 3 hours with no task completion recordedWatchdog triggered to evaluate the stalled task. If agent is hung, recovery initiated.
Boot thrashingDroplet has been powered on and off more than 5 times in a single hourIdle timeout extended to 45 minutes for the remainder of the hour to prevent repeated boot cycles.
Zombie dropletDroplet is ON and billing, but no heartbeat received for more than 30 minutes and no task is activePower off immediately. Log the zombie duration for billing reconciliation.
Cost spikeDeveloper's daily spend exceeds 3× their 30-day rolling daily averageOperator alert. No automatic action — the developer may legitimately be having an unusually productive day.
Idle accountDeveloper has submitted no tasks for 7 consecutive days and droplet storage is still allocatedOperator alert. Storage snapshot created. Droplet retained for 14 more days then destroyed if no activity.

DigitalOcean API Usage #do-api

The Resource Controller uses exactly four DigitalOcean API endpoints. No other DO API calls are made by this component. This minimal surface area makes the integration simple to audit, test, and maintain.

OperationEndpointWhen Called
Power on dropletPOST /v2/droplets/{id}/actions body: {"type":"power_on"}Work queued while droplet is off, or pre-warm trigger fires
Power off dropletPOST /v2/droplets/{id}/actions body: {"type":"power_off"}Idle timeout reached, zombie detected, or Watchdog orders shutdown
Get droplet statusGET /v2/droplets/{id}Polled every 10 seconds during boot to detect when droplet is ready
List droplet actionsGET /v2/droplets/{id}/actionsUsed to verify power-on/off action completed successfully

All API calls are authenticated with a DigitalOcean personal access token scoped to droplet read/write only — no other DO resource types. The token is stored in the platform's secrets manager, not in any config file or environment variable in plaintext.

Tier Assignment #tier-assignment

The GPU tier for a task is determined by the LLM Selector (see Spec E) based on task type and complexity. The tier is written into the task descriptor as the gpu_tier field before the task enters the QUEUED state. The Resource Controller reads this field and ensures the developer's droplet matches the required tier before dispatching.

If a developer's assigned droplet is Tier 2 and a Tier 1 task arrives, the Resource Controller either: uses the Tier 2 droplet with a smaller model variant if one is available that fits in 48 GB VRAM, or provisions a temporary Tier 1 droplet for this task only and powers it off immediately on completion. The per-developer default droplet tier is configured per developer account and does not change dynamically — only task-level overrides trigger temporary higher-tier provisioning.

Cost Math #cost-math

The following calculation shows the monthly GPU cost for a typical developer at 25% utilization on the default Tier 2 (L40S) droplet, compared to always-on:

Working days per month: 22 days
Working hours per day: 8 hours
Active utilization rate: 25% (2 hours active per 8-hour day)
Active GPU hours per month: 22 × 2 = 44 hours
Idle overhead (pre-warm, etc): +15% = 50.6 hours billed
L40S rate: $1.57/hr
Monthly GPU cost (RC managed): $79.44
Always-on comparison: 730 hrs × $1.57 = $1,147/month
Monthly saving per developer: $1,067.56 (93% reduction)

The $94/month figure used in the index document includes $79.44 in GPU compute plus approximately $14.56 for storage, snapshot retention, and intra-datacenter networking for the droplet.

Multi-Cloud Provisioner #multi-cloud

The Multi-Cloud Provisioner provides a cloud-agnostic abstraction over multiple GPU cloud providers. All other platform components provision infrastructure by calling the Provisioner's interface — they never interact with a cloud provider's API directly. The Provisioner selects the cheapest available GPU matching the request's requirements and handles all provider-specific API differences internally.

Pricing Engine #pricing-engine

The Pricing Engine is a background process that polls all supported cloud providers every 15 minutes and updates the price table in Redis. For providers with fixed pricing (DigitalOcean, Lambda Labs), the poll verifies the current published rate. For spot/marketplace providers (AWS Spot, Vast.ai), the poll fetches the current market price which can change minute to minute.

Cloud Selection Algorithm #selection-algorithm

When a provisioning request arrives, the Provisioner evaluates all available options that satisfy the minimum requirements and selects the cheapest one. The selection applies a set of filters in sequence — any option failing a filter is excluded from consideration.

  1. VRAM filter: Exclude all options with less VRAM than the model requires. A 32B model at 4-bit quantization requires ~20 GB VRAM minimum; 48 GB is preferred for headroom.
  2. Availability filter: Exclude options where available: false in the price table. Availability is refreshed every 15 minutes — a just-sold-out instance type may appear available briefly.
  3. Reliability filter: Exclude Vast.ai for QUEUED tasks with a priority of 1 or 2. Vast.ai's consumer hardware reliability variance makes it unsuitable for high-priority blocking work.
  4. Data residency filter: For tenants with data residency requirements (e.g. EU data must stay in EU), exclude options in non-compliant regions.
  5. Spot interruption filter: For tasks with estimated duration over 2 hours, apply a 20% premium to spot pricing to account for interruption risk and re-provisioning cost.
  6. Price sort: From remaining options, select the lowest effective hourly rate.

Cloud Failover #failover

When a provisioned cloud resource fails (droplet crash, spot instance interruption, provider outage), the Resource Controller signals the Provisioner to provision a replacement. The Provisioner runs the selection algorithm again, excluding the failed provider from consideration for the next 30 minutes. It provisions on the next cheapest available option and signals the Watchdog that a replacement is ready for the task to resume.

Failover sequence:

  1. Watchdog detects droplet is unreachable for 2 consecutive health checks (2 minutes).
  2. Watchdog signals Resource Controller: droplet {id} on provider {provider} is down.
  3. Resource Controller marks the failed provider as unavailable for 30 minutes in Redis.
  4. Multi-Cloud Provisioner runs selection algorithm (failed provider excluded).
  5. New instance provisioned on best available alternative. Takes 60–120 seconds.
  6. MASTER_CONTEXT.md read. Task resumes from last checkpoint on new instance.
  7. Jira comment posted: "Infrastructure failure on [provider]. Task resumed on [new provider] with no work lost."

Cloud Abstraction Interface #abstraction-layer

Each cloud provider is implemented as an adapter conforming to the CloudProvider interface. Adding a new cloud provider requires implementing this interface only — no other platform code changes.

// CloudProvider interface (Python)
class CloudProvider(ABC):

    @abstractmethod
    def provision(
        self,
        vram_gb_min: int,
        duration_estimate_hrs: float,
        region_constraint: str | None
    ) -> ProvisionedInstance:
        """
        Provision an instance meeting requirements.
        Returns ProvisionedInstance with id, ip, provider,
        actual_vram_gb, price_per_hr, and ssh_key_path.
        """

    @abstractmethod
    def terminate(self, instance_id: str) -> bool:
        """Terminate the instance. Returns True on success."""

    @abstractmethod
    def get_status(self, instance_id: str) -> InstanceStatus:
        """Returns: BOOTING | RUNNING | STOPPING | STOPPED | ERROR"""

    @abstractmethod
    def get_current_pricing(self) -> list[PriceEntry]:
        """Returns current available GPU options with prices."""
