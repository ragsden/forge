Functional Spec Generator & Jira Integration
How a one-line product requirement becomes a complete functional specification, a detailed task list, a dependency graph, Jira tickets, and the source of all pipeline work.
Components: 04, 05, 06 Version: 1.0 Status: Draft May 2026

Overview #overview

The intake layer is the entry point for all work in the FORGE platform. It is the bridge between the product owner's intent and the pipeline's execution. It consists of three components: the Functional Spec Generator Agent, the Jira Integration Layer, and the FORGE Bot Identity.

The design principle here is that Jira is the source of all work. The pipeline only acts on what exists in Jira. No work is invented by the platform. No work bypasses the product owner's approval. The Functional Spec Generator converts natural language intent into structured, approved, traceable Jira tickets — and only then does the pipeline begin.

Core Workflow
Product owner submits one line → Spec Generator converses until it has enough → Spec Generator produces functional spec + task list + dependency graph → Product owner reviews and edits → Product owner approves → Jira tickets created → Pipeline begins.

Functional Spec Generator Agent #spec-generator

The Functional Spec Generator Agent is an LLM-powered agent that conducts a structured conversation with the product owner. Its job is to take a one-line requirement and produce a complete, unambiguous functional specification with no missing information. It is the only agent in the platform that interacts directly with a human in real time.

Conversation Design #conversation-design

The conversation is not a form. It is not a list of fields to fill in. It is a genuine dialogue where the agent builds up its understanding of the requirement incrementally, asking the most important open question at each step, until it has enough to write a complete specification without further input.

The agent maintains an internal model of what it knows and what it still needs. It does not ask questions whose answers can be inferred. It does not ask for information that is not relevant to the current requirement. It stops asking as soon as it has enough — not when a fixed number of questions have been asked.

Question Strategy #question-strategy

At each turn the agent evaluates its internal knowledge gaps and selects the single most important one to ask about. The prioritization order for what to ask is:

  1. Scope boundary — what is explicitly in and out of scope. Without this the task list cannot be bounded.
  2. External dependencies — third-party services, APIs, or libraries the feature relies on. Required to define input interfaces.
  3. Edge cases and error states — what happens when things go wrong. Required to write meaningful acceptance criteria.
  4. Performance expectations — latency, throughput, concurrency. Required to configure the Performance Agent thresholds.
  5. Security and compliance constraints — data handling, authentication, regulatory requirements. Required to configure the Security Agent.
  6. Integration points with existing features — which existing code this feature reads from or writes to. Required to define dependency links.

The agent never asks about implementation details. It never asks which programming language to use (that is determined by the project configuration). It never asks about internal architecture (that is the Code Agent's responsibility). It only asks what a product owner can reasonably be expected to know about their own requirement.

Hard Rule
The agent asks exactly one question per turn. It never presents a numbered list of questions. If it has multiple knowledge gaps, it picks the most important one and asks only that. The product owner should never feel interrogated.

Spec Output Format #spec-output

After the conversation ends, the agent produces three artifacts simultaneously. All three are presented to the product owner for review before anything is written to Jira.

ArtifactContentPurpose
Functional SpecificationWritten prose document: overview, scope, user flows, edge cases, error states, performance expectations, security constraints, out-of-scope itemsHuman-readable record of what is being built and why. Stored in Jira as an Epic description.
Task ListOrdered list of tasks, each with full schema (see below)The decomposed implementation work. Becomes Jira Story tickets.
Dependency GraphVisual DAG showing which tasks block whichPresented for product owner review and editing before approval.

The functional specification includes an explicit Out of Scope section. This section is as important as the scope itself — it prevents the platform from generating tasks for work the product owner did not intend. The agent populates this section based on common adjacent features that the requirement text might imply but which were not explicitly requested.

For the cryptocurrency example, the Out of Scope section would include: support for additional cryptocurrencies beyond BTC and ETH, fiat-to-crypto conversion UI, wallet address book, transaction history page, crypto refunds (noted as a follow-on feature), and mobile payment flow differences.

Task Decomposition #task-decomposition

After generating the functional specification, the agent decomposes it into the minimum set of atomic tasks required to implement it. An atomic task is one that a single Code Agent session can complete — it has clear boundaries, defined inputs and outputs, and can be tested independently.

The agent avoids creating tasks that are too large (would require multiple Code Agent sessions), too small (would be trivially grouped with an adjacent task), or ambiguous (could be interpreted in more than one way). Each task should represent a deliverable that makes sense on its own — a service, a handler, a module, a migration, a configuration — not a step in a process.

Dependency Graph #dependency-graph

The Spec Generator produces the initial dependency graph. Dependencies are inferred from the input/output interface relationships between tasks. If Task B lists an output of Task A as one of its inputs, then B depends on A — the Spec Generator sets this automatically.

The dependency graph is presented visually in the approval interface. The product owner can: add a dependency edge, remove a dependency edge, merge two tasks into one, split one task into two, change a task's priority, or mark a task as manual (will not be executed by the pipeline, only tracked). All edits are reflected in real time in the visual graph before the product owner submits approval.

Product Owner Approval #approval-flow

No ticket is created in Jira and no pipeline work begins until the product owner explicitly approves the full specification and task list. This is a hard gate — it cannot be bypassed by configuration or by any agent.

Approval Interface #approval-ui

The product owner sees three panels simultaneously:

Product Owner Approval View
Panel 1 — Functional Specification
Full written spec in readable prose. Includes scope, out of scope, user flows, edge cases, error states, and performance expectations. Read-only — the product owner cannot edit this panel but can request the Spec Generator to revise it by typing a change request.
Panel 2 — Task List
Every task displayed as an editable card. Product owner can: modify any field, change priority, change assigned developer, change coverage threshold, remove a task entirely, or mark a task as manual. The Spec Generator re-validates the task list after any edit and flags any resulting gaps or conflicts.
Panel 3 — Dependency Graph
Interactive visual DAG. Product owner can drag to add/remove dependency edges. Changes are reflected immediately in the task cards. Circular dependencies are highlighted in red and must be resolved before approval can be submitted.

Creating New Tasks #new-task

The product owner can add entirely new tasks that were not generated by the Spec Generator. This covers cases where the product owner knows additional implementation details that did not come up in the conversation — for example, a specific database migration or a configuration change in an infrastructure component.

When the product owner types a new task description, the Spec Generator Agent assists by auto-populating the task schema: inferring acceptance criteria from the description, suggesting dependency links based on the files_to_write field and existing tasks' output interfaces, and estimating duration and cost. The product owner can override any auto-populated field.

New tasks created during approval go through the same pipeline as Spec Generator-created tasks. They are not treated differently by any agent.

The product owner can also add new tasks at any time after approval — even while the pipeline is running — by returning to the approval interface, adding the task, and submitting it as a standalone approval. The Scheduler picks up new CREATED tasks on its next DAG rebuild cycle.

Jira Integration Layer #jira-integration

The Jira Integration Layer is the component responsible for all reads and writes between FORGE and the external project management system. It operates as a service that the Master Scheduler, all agents, and the Spec Generator call — no component writes to Jira directly. All Jira writes go through this layer, which handles authentication, rate limiting, retry logic, and field mapping.

Ticket Creation on Approval #ticket-creation

When the product owner clicks Approve, the Integration Layer creates all tickets in a single batched operation in this order:

  1. Create the Epic ticket from the functional specification. The Epic description contains the full functional spec prose. The Epic links to all Story tickets created in subsequent steps.
  2. Create one Story ticket per task, in dependency order (leaf tasks first — tasks with no dependencies — so that dependency links can be set correctly on creation).
  3. Set Jira "is blocked by" links between tickets according to the dependency graph.
  4. Set initial status of all tickets to CREATED.
  5. Assign all tickets to the FORGE Bot identity.
  6. Write a comment on the Epic: "FORGE Bot: Specification approved by [product owner name] at [timestamp]. [N] tasks created. Pipeline starting."

The entire batch creation is atomic from the Jira perspective — if any ticket creation fails, the Integration Layer rolls back all created tickets and alerts the product owner with the error. The product owner can retry the approval without re-running the conversation.

Status Updates During Pipeline #status-updates

Every agent is responsible for triggering a Jira status update when it starts and completes a task. The agent does not write to Jira directly — it includes the desired status transition in its result payload, and the Integration Layer executes the write. This keeps all Jira writes serialized through one component.

In addition to status changes, FORGE Bot adds a comment at every significant pipeline stage transition. These comments are written in plain language that a non-technical product owner can understand. Below are examples of what appears in the Jira ticket activity stream as a task progresses:

FORGE Bot Identity #forge-bot

FORGE Bot is a service account in the project management system. From Jira's perspective it is a team member — it can be assigned tickets, it can comment, it can transition statuses, it can open PRs, and it can log time. The team sees FORGE Bot in the assignee field and in the activity stream exactly as they would see a human developer.

FORGE Bot is configured with the following permissions in Jira:

  • Create issues of types: Story, Bug, Security Bug, Performance Bug, Sub-task
  • Transition issue statuses for all issue types
  • Add comments to any issue
  • Edit issue fields: assignee, priority, labels, description, acceptance criteria (custom field)
  • Link issues: "is blocked by", "blocks", "relates to", "is duplicated by"
  • Log work against issues
  • Create and edit sprints (if sprint-based workflow is configured)

FORGE Bot does not have permission to: delete issues, modify project configuration, change workflow definitions, or access issues outside its assigned project scope.

Rate Limiting and Reliability #rate-limits

The Integration Layer maintains a write queue per tenant with a maximum of 10 writes per second to stay within Jira's API rate limits. Writes are prioritized in this order: status transitions (highest priority), PR links, bug ticket creation, comments, time logging (lowest priority).

Comments are coalesced: if multiple comments are queued for the same ticket within a 5-second window, they are combined into a single API call with each message as a separate paragraph. This reduces API call volume significantly during active pipeline stages.

Failed Jira writes are retried with exponential backoff: 1 second, 2 seconds, 4 seconds. After 3 failed retries the write is added to a dead-letter queue, the operator is alerted, and the write is retried once per minute until it succeeds or until the operator manually clears it. The pipeline continues regardless of Jira write failures — Redis is the source of truth for pipeline state.
