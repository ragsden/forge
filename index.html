Executive Summary

FORGE is an autonomous software engineering platform for any organization that builds software. A product owner describes what they want in plain language. FORGE conducts a structured conversation, generates a complete functional specification, decomposes it into detailed tasks, creates those tasks in the organization's project management system, and then autonomously builds, tests, secures, performance-validates, and deploys production-grade software — without a human developer writing a single line of code.

The platform is built around a pipeline of eight specialized AI agents coordinated by a Master Scheduler. Agents communicate exclusively through structured JSON contracts. The platform self-heals on failure, routes errors back automatically, creates bug tickets in Jira for every issue found, and suspends only when a problem genuinely requires human judgment. All work is tracked in Jira — the platform behaves exactly as a human development team would, but operates 24 hours a day, 7 days a week, at a fraction of the cost.

FORGE is language-agnostic. It supports any programming language through a pluggable executor interface in the Build and Test agents. It is cloud-agnostic, provisioning GPU compute on demand from multiple cloud providers and selecting the cheapest available option that meets the hardware requirements. It is model-agnostic, selecting the best open-source LLM for each task type and automatically migrating to better models as they are released. Each customer's codebase is used to fine-tune the platform's models with zero manual labeling, so the platform gets smarter about each company's specific patterns every week.

The platform is designed for multi-tenant operation at scale — 100 concurrent developers, each with isolated infrastructure, independent pipelines, and a shared dependency resolution layer that eliminates merge conflicts and coordination overhead. Resiliency is built into every layer: heartbeat monitoring, automatic recovery from agent and infrastructure failures, separate retry counters for resiliency and code failures, and a Watchdog that continuously monitors every active task.

Core Value Proposition
A product owner submits a one-line requirement. FORGE delivers deployed, tested, secured, production-grade software. The entire software development supply chain — specification, implementation, testing, security, performance validation, deployment — is automated end to end.

§2 — Complete Component Inventory

FORGE consists of 29 components across six architectural layers. Every component listed here is specified in full detail in one of the six component specification documents.

Layer 1 — Orchestration
01
Master Scheduler
Central coordinator. Owns the task DAG, manages state machine transitions, dispatches agents, enforces cost caps, handles human escalation. The only component with write access to the global task state.
02
Watchdog
Subprocess of the Master Scheduler. Monitors all active agent heartbeats, task status timeouts, droplet health, and Jira sync consistency every 60 seconds. Executes the recovery decision tree on any detected failure.
03
State Store (Redis)
Lightweight internal source of truth for heartbeats, progress checkpoints, retry counters, and task state. Updated every 30 seconds by each active agent. Kept in sync with Jira by the Jira Integration Layer.
Layer 2 — Intake & Project Management
04
Functional Spec Generator Agent
Conducts a structured one-question-at-a-time conversation with the product owner. Converts a one-line requirement into a complete functional specification, a detailed task list, and a proposed dependency graph. Presents all three for approval before anything is created in Jira.
05
Jira Integration Layer
Write-only on task creation (triggered by product owner approval). Read-write during pipeline execution for status updates, comments, time logging, bug ticket creation, and PR linking. Maintains sync between Redis state store and Jira. Supports Jira, Linear, GitHub Issues, Asana, and Azure DevOps.
06
FORGE Bot Identity
Service account that the platform acts as inside the project management system. Appears as a team member — assignee, commenter, PR author, time logger. Indistinguishable in workflow from a human developer.
Layer 2b — Architecture
29
Architecture Agent
Runs after functional spec approval, before Code Agent. Designs the complete technical architecture: service boundaries, data model, interface contracts, technology choices, and Architecture Decision Records (ADRs). Creates all implementation tasks in Jira with exact file paths, interface references, and architecture-derived acceptance criteria. Uses Llama-3.1-70B on H100. 8,192 token budget. → Full spec
Layer 3 — Agent Pipeline
07
Code Agent
LLM-powered. Dequeues QUEUED tasks and QUEUED bugs from Jira. Writes source files and unit test files simultaneously. Emits heartbeat every 30 seconds. Writes MASTER_CONTEXT.md checkpoint after every file. Hard token budget: 4,096 output tokens per call.
08
Build Agent
Language-agnostic via pluggable executor interface. Runs the appropriate compiler or build tool for the project's language. Rule engine handles ~80% of errors at zero LLM cost. Claude Haiku for unknown errors. Outputs structured JSON error report.
09
Security Agent
Runs after every successful build. Checks for CVEs in dependencies (OSV, NVD, Snyk databases), hardcoded secrets, SAST vulnerability patterns, license compliance, and SOC 2 relevant controls. Creates Bug tickets in Jira for all findings. Blocks pipeline on Critical and High severity.
10
Test Agent
Runs the unit test suite written by the Code Agent. Measures coverage against per-task thresholds. Uses Claude Haiku as LLM-as-Judge to evaluate test quality beyond pass/fail. Creates Bug tickets per failure. CPU droplet only.
11
Performance Agent
Runs k6 load tests. Measures p50/p95/p99 latency, RPS, memory, CPU, and error rate. Captures CPU flame graphs. Claude Haiku interprets profiling data and identifies root cause. Creates Bug tickets for any threshold breach. L40S GPU on-demand.
12
Log Monitor Agent
Continuous log ingestion via Fluentd → Redis stream. Claude Haiku streaming detects anomalies — repeated exceptions, latency spikes, OOM, novel multi-signal failures. Creates Jira bug tickets automatically. Triggers on-demand GPU for Code Agent when fix is needed. CPU droplet only during monitoring.
13
Audit Agent
Called when pipeline failures cannot be routed to a specialist agent. Rule engine handles ~80% of known patterns at zero LLM cost. Claude Haiku for novel or composite failures. Produces structured fix specifications for the Code Agent.
14
Audit Agent
Called on pipeline failures not handled by the specialist agents. Reads logs and metrics. Rule engine covers ~80% of patterns at zero LLM cost. Claude Haiku for unknown failures. Outputs structured JSON fix spec with instructions[] and do_not_touch[] fields routed back to the Code Agent.
Layer 4 — Resource Management
15
Resource Controller
Manages the lifecycle of GPU droplets per developer. Powers on when work is queued. Powers off after idle timeout. Predictive pre-warming 5 minutes before learned start time. Routes tasks under 500 tokens to Claude API when cheaper than GPU boot cost. Triggers replacement provisioning on droplet failure.
16
Multi-Cloud Provisioner
Cloud-agnostic abstraction over DigitalOcean, AWS EC2 Spot, Lambda Labs, RunPod, Vast.ai, and Paperspace. Pricing engine polls all clouds every 15 minutes. Selects cheapest available GPU matching VRAM requirement. Handles failover when primary cloud is unavailable.
17
GPU Droplet Tier Manager
Assigns the appropriate GPU tier to each task based on the model required. Tier 1: H100 80GB ($3.39/hr) for 70B models. Tier 2: L40S 48GB ($1.57/hr, default) for 32B models. Tier 3: RTX 4000 Ada 20GB ($0.76/hr) for 7B models. Tier 4: CPU only ($0.10/hr) for documentation tasks.
Layer 5 — Intelligence
18
LLM Selector
Classifies incoming tasks by type and routes to the best available model. Considers task type, required quality level, token budget, hardware availability, and cost. Falls back to Claude API when self-hosted model is unavailable or task is below API routing threshold.
19
LLM Registry
Database of all available models with benchmark scores, hardware requirements, cost per token, supported languages, and compatibility flags. Scanned and updated weekly from HuggingFace and public benchmark leaderboards.
20
Knowledge Layer / Ingestion Agent
Reads the customer's codebase, git history, PR review comments, design files, and docstrings. Converts them into training examples with automated quality scoring. Zero manual labeling required. Runs continuously — every merged PR generates new training examples.
21
LoRA Training Orchestrator
Manages fine-tuning runs on automated schedule: weekly Sunday 2am, or triggered by 500+ new examples, new developer joining, or PR approval rate dropping below 75%. Produces a 50–200MB adapter file. Initial training: $25–40. Weekly incremental: $9–15.
22
Model Version Controller
Monitors for new model releases. Runs a 7-day canary migration pipeline: detect → shadow eval → retrain adapter → 5% canary → expand → full migration. Training data is reused as-is. Only the adapter is regenerated. Full migration costs ~$50 and 4–8 hours of compute.
23
LLM-as-Judge Evaluator
Multi-model evaluation panel used to validate adapter quality before promotion: Claude Sonnet (40% weight), GPT-4o (35%), Gemini 1.5 Pro (25%). Position bias correction applied. Evaluates correctness, convention compliance, code quality, performance, and security across five criteria.
Layer 6 — Multi-Tenant & Operations
24
Per-Developer Isolation Manager
Each developer gets a dedicated GPU droplet, dedicated git branch, dedicated Docker environment, and isolated network namespace. One developer's pipeline cannot affect another's in any way.
25
Feature Dependency DAG Resolver
Reads Jira dependency links and builds the execution DAG. Determines correct execution order. Runs independent features in parallel. Detects and flags circular dependencies for human resolution. User can edit dependencies directly in Jira at any time — resolver re-reads and adjusts automatically.
26
Conflict Detector
Pre-pipeline file lock registry. Detects when two concurrent tasks would modify the same file. Queues the lower-priority task until the first is merged. Prevents merge conflicts before they occur.
27
PR Merge Orchestrator
Manages the sequence of PR approvals and merges across all concurrent developers. Ensures main branch remains stable. Coordinates rebase and merge order when multiple PRs are ready simultaneously.
28
Developer Dashboard
Real-time view of: active pipelines, task and bug status distribution, GPU cost vs. budget, PR approval rates, test coverage trends, security finding counts, performance metric trends, and active anomaly alerts. Per-developer and per-team views.

The JSON Contract Principle

All inter-agent communication is structured JSON. No agent ever receives or sends free-text instructions to another agent. Every input and every output crossing an agent boundary is a valid, schema-conforming JSON object. This makes the system deterministic, observable, and debuggable. Any failure can be traced to the exact JSON payload that triggered it.

Jira as External Source of Truth

Jira (or the configured project management system) is the authoritative external record of all work. The Redis state store is the authoritative internal record. The two are kept in sync by the Jira Integration Layer. When there is a conflict between internal state and Jira — for example after a network partition — the Watchdog detects the inconsistency and re-syncs, using Redis as the source of truth for pipeline state and writing the correct status back to Jira.

Language Agnosticism

The Build Agent and Test Agent are language-agnostic by design. Each supports a pluggable executor interface. A language executor is a self-contained adapter that knows how to: invoke the build tool for that language, parse its output into the standard JSON error schema, run the test suite, and parse coverage output into the standard JSON coverage schema. Adding a new language requires writing one executor adapter — the core agent logic does not change.

Supported language executors at launch: Rust (cargo), Python (pytest/setuptools), TypeScript/JavaScript (npm/jest), Go (go build/go test), Java (maven/gradle/JUnit), Ruby (bundler/rspec), Swift (swift build/XCTest).

§4 — Jira-Centric Workflow

§5 — Resiliency Model

The Heartbeat System

Every agent emits a heartbeat to the Redis state store every 30 seconds while active. The heartbeat includes the agent ID, task ID, current status, start time, last beat time, a progress note, and the current retry count. The Watchdog reads all active heartbeats every 60 seconds.

Recovery Scenarios

Agent Crashed

Heartbeat stops. Watchdog detects after 3 minutes. Checks git branch for committed work. If no work committed: moves task to QUEUED, increments resiliency retry count, adds Jira comment, spins up fresh agent. If partial work committed: rolls back partial commit, moves to QUEUED. If complete work committed: advances to next stage normally.

GPU Droplet Down

Droplet health ping fails for 2 minutes. Watchdog signals Resource Controller. Resource Controller attempts droplet restart via cloud API. If restart fails within 3 minutes, Multi-Cloud Provisioner provisions a replacement on the next cheapest available cloud. Git branch is checked for committed work and evaluated as above. Jira comment added with full detail of what happened and what was recovered.

Agent Hung

Heartbeat present but progress note unchanged for 2× the expected duration. Watchdog sends SIGTERM. Waits 30 seconds. If no clean shutdown, sends SIGKILL. Evaluates committed work, requeues task, increments retry count, spins up fresh agent.

Jira Sync Inconsistency

Redis state and Jira status disagree for more than 10 minutes. Watchdog attempts re-sync from Redis to Jira. If re-sync fails 3 times, operator is alerted and pipeline continues using Redis as truth, writing the correct status back to Jira when connectivity is restored.

Retry Counter Separation

Resiliency retries (infrastructure failures) and code failure retries (build errors, test failures) are tracked with separate counters on every task and bug ticket. A task can exhaust 3 resiliency retries and still have 3 code failure retries remaining, and vice versa. This prevents an unlucky infrastructure failure from consuming the code failure budget.

MASTER_CONTEXT.md as Recovery Document

Every agent writes a checkpoint to MASTER_CONTEXT.md after every meaningful unit of progress — not just at completion. For the Code Agent this means after every file written. When a fresh agent picks up a requeued task it reads the checkpoint first and continues from where the crashed agent left off. Maximum size: 3,000 tokens, enforced on every write.

§6 — Multi-Tenancy & Scale

Customer-Level Isolation

Each customer organization is a completely isolated tenant. No data, model adapters, training examples, code, logs, or infrastructure is shared between customers. Each customer has their own fine-tuned model adapter trained exclusively on their codebase. Customer data never leaves their designated cloud region unless explicitly configured otherwise.

Developer-Level Isolation

Within a customer organization, each developer has a dedicated GPU droplet, a dedicated git branch namespace, a dedicated Docker environment, and an isolated network namespace. One developer's pipeline failure cannot affect another developer's pipeline in any way.

Feature Dependency DAG at Scale

With 100 developers submitting features concurrently, the dependency graph can become complex. The DAG Resolver handles this by: reading all Jira dependency links on a 30-second polling interval, rebuilding the execution DAG on every change, identifying the maximum parallelism available given current dependencies, and dispatching independent tasks to available developer droplets immediately. Circular dependency detection runs on every DAG rebuild — if a cycle is found, the involved tasks are moved to SUSPENDED with a detailed explanation.

Conflict Detection at Scale

The Conflict Detector maintains a file lock registry in Redis. Before any task enters IN PROGRESS, the Code Agent claims locks on all files it will modify (read from the task descriptor's output interfaces field). If another task already holds any of those locks, the second task waits in QUEUED until the first task's PR is merged and locks are released. This prevents merge conflicts entirely — two agents never write to the same file simultaneously.
