Specification G — New Component
Architecture Agent
The design brain of the platform — converts approved requirements into a complete, unambiguous technical architecture before a single line of code is written. Creates and owns all implementation tasks in Jira.
Component: 29 Version: 1.0 Status: Draft May 2026

Overview #overview

The Architecture Agent is a new agent that runs after product owner approval and before the Code Agent. Its job is to convert the approved functional specification into a complete technical architecture — defining service boundaries, data models, interface contracts, and technology choices — and then decompose that architecture into concrete, atomic implementation tasks that are created directly in Jira.

Before the Architecture Agent, task creation happened during the Spec Generator conversation — producing task outlines based on business requirements. This was sufficient for simple features but produced incomplete task descriptors for complex features: missing interface definitions, vague file structures, no data schema, and no explicit technology choices. The Code Agent was then forced to make architecture decisions during code generation, leading to inconsistencies across tasks.

With the Architecture Agent, there is a complete separation of concerns: the Spec Generator understands business requirements, the Architecture Agent understands technical design, and the Code Agent understands implementation. Each stays in its lane.

Core Principle
The Architecture Agent is the only component that makes technology decisions. The Code Agent implements them. The Spec Generator captures business intent. No agent crosses into another's domain.

Pipeline Position #position

Product Owner → one-liner requirement ↓ Functional Spec Generator → conversation → functional spec ↓ Product Owner → reviews spec → approves ↓ ▶ ARCHITECTURE AGENT ← THIS AGENT Reads functional spec Designs complete technical architecture Creates all implementation tasks in Jira Writes architecture to MASTER_CONTEXT.md ↓ Product Owner → reviews architecture + tasks → approves ↓ Master Scheduler → builds execution DAG from task dependencies ↓ Code Agent → dequeues tasks → writes code against architecture contracts ↓ Build → Security → Test → Performance → Deploy → Integration

The Architecture Agent introduces a second human approval gate — the first approves the functional spec and business requirements, the second approves the technical architecture and task list. This ensures that a product owner who submits a requirement is not surprised by the implementation approach, and that a tech lead has the opportunity to review and modify the architecture before any code is written.

Responsibilities #responsibilities

The Architecture Agent has three primary responsibilities that are explicitly outside the scope of any other agent:

ResponsibilityWhat It MeansWhat It Does Not Do
Technology selectionChooses the database, framework, message queue, caching layer, and runtime for each component based on the requirementsDoes not implement any of these choices — that belongs to the Code Agent
Interface definitionDefines every public interface, API endpoint, data type, and event schema that tasks will produce and consumeDoes not write implementation code for those interfaces — only their signatures and contracts
Task creationCreates all implementation tasks in Jira with complete detail, explicit dependencies, and architecture-informed acceptance criteriaDoes not create the initial functional spec tasks — those come from the Spec Generator. Architecture Agent replaces those high-level tasks with concrete implementation tasks.

Five Output Artifacts #artifacts

The Architecture Agent produces five artifacts. All five are stored in MASTER_CONTEXT.md and referenced by every downstream agent. The Code Agent reads them before writing a single line. The Audit Agent reads them when classifying failures. The Log Monitor Agent reads them when verifying acceptance criteria.

Artifact 1
System Architecture Document
Service boundaries, data flow diagrams, technology choices with justification, API contract definitions, external integration points. Written in prose with supporting ASCII diagrams.
Artifact 2
Data Model
Complete schema for every table, collection, or data structure. Relationships, indexes, constraints, and migration strategy. Specified before any Code Agent runs.
Artifact 3
Interface Contracts
Every public interface between tasks explicitly defined. Rust traits, TypeScript interfaces, Python Protocols, HTTP endpoint schemas — the exact signatures the Code Agent implements against.
Artifact 4
Architecture Decision Records
One ADR per significant technology or design decision. Format: Context → Decision → Consequences → Alternatives considered. Immutable once approved — changes require a new ADR.
Artifact 5
Implementation Task List
All tasks with full detail: exact file paths, interface references, acceptance criteria derived from both business requirements and architectural constraints, explicit dependencies.

Artifact 1 — System Architecture Document #arch-doc

The system architecture document is the primary reference for the entire implementation. It defines what gets built at the system level. Example for the customer 360 platform:

# Customer 360 Platform — System Architecture

## Service Boundaries
Single-service architecture: one Rust binary serving all endpoints.
Rationale: 500 concurrent users, single team, no independent scaling
requirements. Microservices would add operational overhead with no benefit.

## Technology Choices
Database:      PostgreSQL 16 — relational data with complex joins required
Cache:         Redis 7 — session storage, 15-min TTL, sub-ms reads
Background:    Tokio async tasks — no separate worker process needed at this scale
Auth:          Okta SAML 2.0 — customer requirement, existing SSO infrastructure
API:           Axum 0.7 — async-first, tower middleware, excellent performance

## Data Flow
Salesforce/Zendesk/Stripe ──► Background Sync Worker (every 15 min)
                                      │
                                      ▼
                              PostgreSQL (unified schema)
                                      │
                                      ▼
                         Axum REST API ──► React Frontend
                                      │
                              Redis (sessions)

## External Integrations
Salesforce:  REST API v58, OAuth 2.0 client credentials flow
Zendesk:     REST API v2, API token auth
Stripe:      SDK v10, webhook signature validation via Stripe-Signature header
Okta:        SAML 2.0 SP-initiated SSO, ACS URL: /auth/saml/callback

Artifact 2 — Data Model #data-model

The data model is specified in full before any Code Agent runs. Every field, type, index, and constraint is defined here. The Code Agent reads this and writes the migration — it does not design the schema.

-- accounts: unified company accounts from all sources
CREATE TABLE accounts (
  id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name          TEXT NOT NULL,
  domain        TEXT,
  salesforce_id TEXT UNIQUE,
  stripe_id     TEXT UNIQUE,
  mrr_cents     INTEGER DEFAULT 0,
  health_score  SMALLINT CHECK (health_score BETWEEN 0 AND 100),
  synced_at     TIMESTAMPTZ DEFAULT NOW(),
  created_at    TIMESTAMPTZ DEFAULT NOW()
);
CREATE INDEX idx_accounts_domain ON accounts(domain);
CREATE INDEX idx_accounts_health ON accounts(health_score);

-- contacts: individuals linked to accounts
CREATE TABLE contacts (
  id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  account_id    UUID REFERENCES accounts(id) ON DELETE CASCADE,
  name          TEXT NOT NULL,
  email         TEXT NOT NULL,
  role          TEXT,
  salesforce_id TEXT UNIQUE,
  zendesk_id    TEXT UNIQUE,
  created_at    TIMESTAMPTZ DEFAULT NOW()
);
CREATE INDEX idx_contacts_account ON contacts(account_id);
CREATE INDEX idx_contacts_email ON contacts(email);

-- sync_events: audit trail of all data sync operations
CREATE TABLE sync_events (
  id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  source     TEXT NOT NULL CHECK (source IN ('salesforce','zendesk','stripe')),
  status     TEXT NOT NULL CHECK (status IN ('success','partial','failed')),
  records    INTEGER DEFAULT 0,
  error      TEXT,
  started_at TIMESTAMPTZ NOT NULL,
  ended_at   TIMESTAMPTZ
);

Artifact 3 — Interface Contracts #interfaces

Every public interface between tasks is defined as a concrete type signature. These are the exact contracts the Code Agent implements. No Code Agent invents an interface — it implements what the Architecture Agent defined.

// Rust trait contracts — defined by Architecture Agent, implemented by Code Agent

pub trait DataSource: Send + Sync {
    async fn sync(&self, since: Option) -> Result<SyncResult, SyncError>;
    fn source_name(&self) -> &'static str;
}

pub struct SyncResult {
    pub records_processed: usize,
    pub records_failed: usize,
    pub errors: Vec<SyncError>,
    pub completed_at: DateTime<Utc>,
}

pub trait AccountRepository: Send + Sync {
    async fn find_by_id(&self, id: Uuid) -> Result<Option<Account>, DbError>;
    async fn search(&self, query: &AccountQuery) -> Result<Page<Account>, DbError>;
    async fn upsert_from_source(&self, account: SourceAccount) -> Result<Account, DbError>;
}

// HTTP API contracts
// GET /api/accounts?search=&page=&per_page=
// Response: { "data": Account[], "total": number, "page": number }

// GET /api/accounts/:id
// Response: AccountDetail (includes contacts, tickets, billing, health_score)

// GET /api/health/:account_id
// Response: { "score": number, "mrr_trend": string, "ticket_volume": number, "csat": number }

Artifact 4 — Architecture Decision Records #adrs

One ADR per significant decision. ADRs are immutable once the architecture is approved. If a downstream agent or human reviewer determines a decision was wrong, a new superseding ADR is created — the original is never edited. This creates a permanent audit trail of why the system was built the way it was.

ADR-001: Single-service architecture over microservices
  Context:     500 concurrent users. Single engineering team. No independent
               scaling requirements for any component.
  Decision:    Single Rust binary with Axum. All components in one service.
  Consequences: Simpler deployment, simpler local dev, single point of failure.
               Cannot scale components independently.
  Alternatives: Microservices (rejected — operational overhead exceeds benefit
               at this scale), Modular monolith with separate DB per module
               (rejected — premature complexity).

ADR-002: PostgreSQL over MongoDB for account storage
  Context:     Account data has well-defined relationships (accounts → contacts
               → events). Complex JOIN queries required for health score.
  Decision:    PostgreSQL 16 with normalized schema.
  Consequences: Strong consistency, excellent JOIN performance, requires
               schema migrations for changes.
  Alternatives: MongoDB (rejected — document model complicates JOIN-heavy
               health score queries), CockroachDB (rejected — overkill for
               single-region deployment).

ADR-003: Redis for session storage, not database
  Context:     Session lookups on every authenticated request. Requirement:
               sub-10ms session validation.
  Decision:    Redis 7 with 15-minute sliding TTL.
  Consequences: Additional infrastructure dependency. Sessions lost on Redis
               restart (acceptable — users re-authenticate).
  Alternatives: PostgreSQL sessions (rejected — 3ms vs 0.3ms, adds DB load),
               In-memory (rejected — doesn't survive restarts).

Artifact 5 — Implementation Task List #task-update

The Architecture Agent replaces the high-level tasks from the Spec Generator with concrete implementation tasks. The Spec Generator produces business-level tasks ("Salesforce data sync"). The Architecture Agent expands these into implementable tasks with exact file paths, interface references, and architecture-derived acceptance criteria.

Where the Spec Generator might produce 5 high-level tasks for the customer 360 platform, the Architecture Agent produces 12 implementation tasks — each scoped to what one Code Agent session can implement cleanly against the defined interfaces.

Task Creation #task-creation

Task creation is the Architecture Agent's most consequential output. Every implementation task that enters the Code Agent's queue was created by the Architecture Agent. The Jira tickets created here are the source of all pipeline work.

1
Spec Generator
Creates high-level business tasks in Jira: "Salesforce sync", "Account detail page", "Health score". These are business-level placeholders — not implementation tasks.
2
Architecture Agent
Reads each business task. Expands into concrete implementation tasks. Creates new Jira tickets with full detail. Links each implementation task back to its parent business task. Archives the high-level placeholder tasks.
3
Architecture Agent
Sets exact file paths in each task's files_to_write field based on the architecture. Sets input_interfaces and output_interfaces from the Interface Contracts artifact. Sets acceptance_criteria that combine business requirements with architectural constraints.
4
Architecture Agent
Sets dependency links between tasks based on interface relationships. If Task B consumes an interface produced by Task A, "Task B is blocked by Task A" is set automatically in Jira.
5
Product Owner
Reviews the architecture document and the full implementation task list. Can edit tasks, change priorities, add tasks, or flag architecture decisions for revision. Approves to start the pipeline.
6
Master Scheduler
Reads all QUEUED tasks from Jira. Builds the execution DAG from dependency links. Dispatches Code Agent instances in parallel waves.

Task Schema Additions #task-schema

The Architecture Agent adds four fields to every task descriptor that the Spec Generator does not populate:

Field
Type
Description
architecture_ref
string
Reference to the section of the Architecture Document that governs this task. e.g. "ADR-002, Data Model §accounts table"
input_interfaces
object[]
Exact interface signatures from Artifact 3 that this task consumes. name, source_task_id, exact_type (the trait or interface definition string)
output_interfaces
object[]
Exact interface signatures this task produces for downstream tasks. Same structure as input_interfaces.
files_to_write
string[]
Exact file paths based on the architecture's directory structure. e.g. ["src/sync/salesforce.rs", "src/sync/mod.rs", "tests/sync/salesforce_test.rs"]
data_model_refs
string[]
Table or collection names from the Data Model artifact that this task reads from or writes to.
technology_constraints
string[]
Specific technology choices from ADRs this task must respect. e.g. "Use Axum extractors, not manual request parsing", "Use sqlx for DB queries, not raw SQL strings"

Jira Behavior #jira-behavior

The Architecture Agent's Jira behavior is distinct from all other agents. It is the only agent that creates tasks — all other agents only update existing tasks and create bug tickets.

Create implementation tasksAfter architecture is designedOne Jira Story per implementation task. Full schema populated including architecture-specific fields. Initial status: CREATED.

Set dependency linksOn task creation"is blocked by" links set based on interface relationships. Automatic — derived from which task produces each input interface.

Downstream Impact #downstream

Code Agent #impact-code

The Code Agent now reads the Architecture Document from MASTER_CONTEXT.md before generating any code. Its context window shrinks dramatically — instead of reasoning about design, it receives design and implements it. Build failures from interface mismatches — the most common failure type in multi-task pipelines — drop significantly because every interface is defined before any task runs.

The Code Agent is explicitly prohibited from making architecture decisions. If it encounters a situation not covered by the Architecture Document, it does not decide — it writes a comment in the code flagging the gap and returns a result JSON with "architecture_gap": true. The Scheduler routes this to the Architecture Agent for a clarification, not back to the Code Agent for a guess.

Audit Agent #impact-audit

The Audit Agent now classifies failures into two categories: code errors and architecture errors. A code error is one where the implementation doesn't match the interface contract — the Code Agent fixes it. An architecture error is one where the interface contract itself is wrong or incomplete — the Architecture Agent issues a revised decision and affected tasks re-enter the queue.

Test Agent #impact-test

Acceptance criteria in task descriptors now include architecture constraints alongside business requirements. For example, a test for the health score endpoint now also verifies that the response time meets the ADR-003 requirement of sub-10ms session validation — not just that the score is calculated correctly.

Log Monitor Agent #impact-integration

The Log Monitor Agent reads the API contracts from the Interface Contracts artifact. It tests the exact endpoint signatures, request/response schemas, and error codes defined by the Architecture Agent — not inferred from the code. This means integration test failures always indicate a real discrepancy between architecture and implementation.

Failure Modes #failure-modes

FailureCauseResolution
Incomplete architecture documentFeature is too large for a single Architecture Agent run within the token budgetScheduler splits the feature into sub-features. Architecture Agent runs once per sub-feature.
Architecture gap discovered by Code AgentA situation arises during implementation that the architecture didn't anticipateCode Agent flags the gap. Architecture Agent runs again with the gap description as input. Issues a supplement ADR. Affected tasks re-enter QUEUED.
Architecture revision requested by reviewerTech lead or architect rejects a technology decision during the architecture reviewArchitecture Agent re-runs with the reviewer's feedback as additional input. Produces revised artifacts. New tasks created. Previous tasks archived.
Conflicting requirements in functional specBusiness requirements contain contradictions the Architecture Agent cannot resolve (e.g. "must be real-time" and "must have zero infrastructure dependencies")Architecture Agent produces a conflict report instead of an architecture document. Product owner is notified. Functional Spec Generator re-runs the conversation to resolve the conflict.

Suspension Conditions #suspension

The Architecture Agent moves the feature to SUSPENDED (human intervention required) when:

  • The same architecture gap is flagged by the Code Agent more than twice — the architecture document is fundamentally incomplete
  • A tech lead rejects the architecture revision three consecutive times — escalation to senior architect required
  • The functional spec contains requirements that are technically impossible given the existing codebase constraints — product owner must revise the requirements
  • The Architecture Agent produces an architecture that the Security Agent immediately flags as having a Critical finding that cannot be resolved without a fundamental redesign
