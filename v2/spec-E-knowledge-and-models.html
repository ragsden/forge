Knowledge Layer & Models
How FORGE learns from each customer's codebase, automatically fine-tunes models with zero human labeling, selects the right LLM for each task, and migrates to better models as they are released.
Components: 18–23 Version: 1.0 Status: Draft May 2026

Overview #overview

The intelligence layer is what makes FORGE a platform that gets smarter over time rather than one that stays static. It has four main capabilities: ingesting a customer's entire codebase and git history to extract training examples automatically; fine-tuning the platform's code generation models on those examples using LoRA adapters; selecting the best available LLM for each task type dynamically; and migrating to better models as they are released without losing any accumulated knowledge.

The central insight driving this layer is that code is self-labeling. A merged pull request is an implicit approval signal. A code review comment paired with the resulting fix is a gold-standard training example. A docstring paired with its implementation is a supervised learning pair. The git history of any active software project is a continuous, free, high-quality training data source — no human annotation required.

The Compounding Effect
Every merged PR generates new training examples. Every weekly training run incorporates those examples. The model gets better at the customer's specific codebase every week. By month 6, context windows are 95% smaller, inference is 10× faster, and PR approval rates reach 94%. The platform's value compounds automatically.

Knowledge Layer / Ingestion Agent #knowledge-layer

Ingestion Pipeline #ingestion

On customer onboarding, the Ingestion Agent performs a full scan of the customer's code repositories. On an ongoing basis, it runs as a background process triggered by git events — every merged PR, every push to a release branch, and every resolved code review comment triggers an incremental ingestion run.

The ingestion pipeline processes the following source types in order of quality signal strength:

  1. Git commit history — full commit log with diffs, commit messages, and author metadata going back to project inception
  2. Pull requests — PR description, commits, review comments, requested changes, and final merged state
  3. Code review comments — inline review comments paired with the before/after diff of the code at that line
  4. Source code files — all source files in all branches, parsed for function signatures, docstrings, type annotations, and inline comments
  5. Test files — unit and integration tests paired with the modules they test
  6. Design documents — architecture docs, API specs (OpenAPI/Swagger), database schemas, README files
  7. Issue and ticket history — Jira/Linear issue descriptions paired with the commits that resolved them

Zero-Labeling Training Sources #zero-labeling

Every training example is extracted automatically from existing artifacts. No human ever manually labels a training example. The following sources produce supervised learning pairs with no annotation work:

Merged Pull Requests
0.85
Merge event = implicit approval label. The PR description is the instruction. The diff is the expected output. Merges are human-approved high-quality completions by definition.
Est. volume: 10–50 examples/week per active developer
Review Comment + Fix Pairs
0.95
A reviewer says "this should use X pattern instead." The developer fixes it. The comment is the instruction. The before/after diff is the gold-standard input/output pair. Highest quality signal in the entire pipeline.
Est. volume: 5–20 examples/week per active reviewer
Docstring → Implementation
0.78
A function with a docstring is a naturally labeled training pair. Docstring = instruction. Function body = expected code output. Works best for well-documented codebases.
Est. volume: hundreds to thousands per codebase scan
Test → Implementation
0.82
A test file describes expected behavior precisely. The implementation satisfying those tests is the expected output. Test-driven codebases produce especially high-quality pairs from this source.
Est. volume: hundreds per codebase scan
Issue → Commit Resolution
0.74
A Jira issue description paired with the commit(s) that closed it. Requires the commit message to reference the issue key. Quality varies with issue description detail.
Est. volume: 5–20 examples/week depending on issue linking discipline
Synthetic Augmentation
0.65
Claude API generates additional training examples by varying existing high-quality examples — different phrasings, edge cases, alternative implementations. Filtered at quality threshold 0.70 before inclusion.
Est. volume: generated on demand for underrepresented patterns
Reverted Commits
0.00
Commits that were later reverted are excluded entirely. A reverted commit is an explicit quality signal of 0 — the code was accepted then rejected. Including it would teach the model to generate bad code.
Automatically detected and excluded via git revert log
CI/CD Pass/Fail Signal
0.80
Code that passed all CI checks gets a higher quality weight. Code that required multiple CI retry cycles before passing gets a lower weight. Binary quality signal that costs nothing to extract.
Applied as a quality multiplier to all other source types

Quality Scoring and Filtering #quality-scoring

Every extracted training example is assigned a quality score between 0.0 and 1.0. Examples scoring below the threshold of 0.70 are excluded from training. This threshold prevents low-signal noise from degrading model quality.

The quality score for an example is computed as:

quality_score = base_source_score
              × ci_pass_multiplier       # 1.0 if all CI passed, 0.8 if retries needed
              × review_approval_factor   # 1.1 if PR had ≥2 approvals, 1.0 otherwise
              × completeness_factor      # 0.5–1.0 based on description length and clarity
              × recency_factor           # slight decay for examples > 12 months old

# Example calculation:
# Review comment + fix:  0.95 × 1.0 × 1.1 × 0.95 × 1.0 = 0.99  ✓ included
# Docstring pair (old):  0.78 × 0.8 × 1.0 × 0.90 × 0.85 = 0.48  ✗ excluded
# Merged PR:             0.85 × 1.0 × 1.0 × 0.95 × 1.0  = 0.81  ✓ included

The quality threshold of 0.70 is a configurable parameter per tenant. Tenants with very large codebases and abundant high-quality examples may raise it to 0.80 to keep the training set lean and high-signal. Tenants with smaller codebases may lower it to 0.65 to maintain sufficient training volume.

Training Example Format #training-example

All training examples are stored in a model-agnostic JSON format. This is the key design decision that makes training data permanent across model migrations — the format does not depend on any specific model's tokenizer or chat template. When a new base model is adopted, the training data is re-tokenized using the new model's tokenizer. The examples themselves never need to be regenerated.

Training Configuration #lora-config

The following LoRA hyperparameters are used for the default Qwen2.5-Coder-32B base model. These values were established through ablation studies and are fixed for the platform's initial release. Per-tenant overrides are available for enterprise customers with dedicated ML engineering support.

ParameterValueRationale
LoRA rank (r)32Balances expressiveness and parameter count. Rank 16 underfits complex coding patterns; rank 64 shows diminishing returns.
LoRA alpha (α)64Alpha = 2× rank is the standard starting point. Controls the effective learning rate scaling of the adapter.
Dropout0.05Light regularization. Code generation benefits from low dropout — too much degrades precision on syntax.
Target modulesq_proj, k_proj, v_proj, o_proj, gate_proj, up_proj, down_projAll attention and MLP projection layers. Broader targeting than attention-only gives better code quality at minimal cost.
Learning rate1e-4Standard for LoRA. Higher rates cause catastrophic forgetting; lower rates slow convergence without quality benefit.
Epochs33 passes over the training set with early stopping on validation loss. More epochs overfit on small company datasets.
Batch size4 (gradient accumulation ×8 = effective 32)Fits H100 80GB VRAM with 32B model in 4-bit quantization.
Sequence length4,096 tokensCovers most training examples. Longer sequences are truncated at natural boundaries (function end).
Quantization4-bit NF4 (bitsandbytes)Reduces base model memory to ~20 GB, leaving 60 GB for adapter training and gradient computation.
OptimizerAdamW with cosine LR scheduleCosine schedule prevents training collapse in the final epochs.
Hardware1× H100 80GBSingle H100 is sufficient for 32B model LoRA training at these settings.
Training duration3–5 hoursVaries with dataset size. Enforced hard stop at 6 hours regardless.

Adapter Lifecycle #adapter-lifecycle

Adapter files are versioned and retained. Every training run produces a new versioned adapter. The previous adapter is never deleted until the new one has been validated and promoted to production. This makes rollback trivial — it is a single file pointer change in the Model Registry, taking less than one second.

Adapter versioning in Model Registry:

  acme-corp/qwen2.5-coder-32b/
    adapter-v1.0/  (initial training, 2026-05-01)
    adapter-v1.1/  (weekly run #1, 2026-05-08)
    adapter-v1.2/  (weekly run #2, 2026-05-15)  ← current production
    adapter-v1.3/  (weekly run #3, training)     ← in validation

  Production pointer: adapter-v1.2
  Validation pointer: adapter-v1.3

Promotion sequence:
  1. adapter-v1.3 completes training
  2. LLM-as-Judge evaluates v1.3 vs v1.2 on held-out test set
  3. If v1.3 scores ≥ v1.2 on all criteria: promote to production
  4. If v1.3 regresses on any criterion: discard v1.3, alert operator
  5. Production pointer updated — zero downtime

Context Window Impact #context-impact

The reduction in context window size is the most directly measurable economic benefit of fine-tuning. A generic model needs extensive context to understand the codebase's patterns, conventions, and interfaces on every call. A fine-tuned model already knows these patterns — the context window only needs to contain the specific task, not a tutorial on how the codebase works.

LLM Selector #llm-selector

The LLM Selector determines which model to use for each incoming task before the task enters the QUEUED state. It writes the selected model identifier and required GPU tier into the task descriptor. All other components use these fields — they never select a model themselves.

Task Classification #task-classification

The Selector classifies tasks into one of the following types based on the task descriptor fields — primarily task_type, language, description length and complexity signals, and output_interfaces breadth:

Task ClassClassification SignalsExamples
Standard code generationSingle module, defined input/output interfaces, language is in supported setImplementing a service, writing an API handler, building a data model
Complex code generationMultiple modules, cross-cutting concerns, novel algorithmic component, 6+ files_to_writeDistributed consensus implementation, query optimizer, graph traversal engine
Architecture designtask_type=architecture, output_interfaces contains multiple new service definitionsDesigning a new microservice, defining a data pipeline, specifying a caching strategy
UI / frontendlanguage=typescript/javascript AND framework signals (React, Vue, Svelte)Component implementation, page layout, state management
Documentationtask_type=docs OR files_to_write contains only .md/.rst filesREADME, API docs, architecture decision records
Configurationfiles_to_write contains only .yaml/.toml/.json/.env filesDocker Compose, CI config, infrastructure as code
Bug fix — simpletask_type=bug AND single file, single function scopeOff-by-one error, wrong return type, missing null check
Bug fix — complextask_type=bug AND multiple files OR architectural root causeRace condition, memory leak, incorrect state machine transition

Fallback Behavior
The company adapter is always the primary model when available and the task requires the Code Agent. If the GPU droplet is unavailable, booting, or the task is below the API routing threshold, the Selector falls back to the Claude API. The fallback always uses the same or better quality model — it never routes to a lesser model to save cost at the expense of quality.

LLM Registry #llm-registry

The LLM Registry is a database of all available models maintained by the platform. The LLM Selector reads from it. The Model Version Controller writes to it when new models are discovered or promoted. It is the authoritative record of what models exist, what they can do, and what they cost.

Weekly Registry Update #registry-update

Every Monday at 03:00 UTC, the Model Version Controller scans HuggingFace Hub for newly released models in the coding, instruction-following, and reasoning categories. It checks benchmark leaderboards (HumanEval, MBPP, BigCodeBench, LiveCodeBench) for models outperforming current catalog entries. If a new model exceeds the current primary model on 2+ benchmarks, it is flagged as a migration candidate and the migration pipeline begins.

Model Version Controller #model-version-controller

The Model Version Controller manages the lifecycle of base model upgrades. When a better model becomes available, it orchestrates the migration over 7 days — evaluating, retraining the adapter, canary testing, and promoting — with full rollback capability at every stage. Human effort required: reading one summary email.

Migration Triggers #migration-triggers

TriggerConditionAction
Benchmark outperformanceNew model exceeds current model on 2+ standard benchmarks by ≥3%Begin evaluation phase automatically
Significant quality gapNew model exceeds current by ≥10% on any single benchmarkExpedited evaluation — 3-day pipeline instead of 7-day
Security vulnerabilityCurrent model has a disclosed vulnerability requiring upgradeEmergency migration — expedited with operator notification
Manual triggerOperator or Anthropic engineering requests evaluation of a specific modelBegin evaluation phase on specified model

7-Day Migration Pipeline #migration-pipeline

Day 0 — Detection
New model identified and flagged
Model Version Controller detects new model exceeds current model on benchmarks. Operator receives automated email with benchmark comparison. Migration pipeline starts. No customer impact.
Day 1 — Shadow Evaluation
New model runs in shadow mode
New model receives 5% of production tasks in parallel with the current model. Its outputs are evaluated by LLM-as-Judge against the current model's outputs. Real tasks, no production impact, outputs discarded. Evaluation runs for 24 hours to accumulate 500+ comparison pairs.
Day 2 — Adapter Retraining
LoRA adapter regenerated for new base model
The existing training data (model-agnostic JSON) is re-tokenized for the new model's tokenizer. LoRA adapter is trained on the new base model using the same hyperparameters. Takes 3–5 hours on H100. Training data is never regenerated — only the adapter changes. Cost: ~$25–40.
Day 3 — Canary Deployment
New model + adapter serves 5% of traffic
New model with retrained adapter promoted to production for 5% of tasks. LLM-as-Judge monitors quality continuously. Automated rollback triggers if quality drops below current model on any criterion. Human can manually rollback via dashboard at any time.
Day 5 — Canary Expansion
Traffic expanded to 25% then 50%
If Day 3–4 canary shows no regressions, traffic expanded in steps: 25% on Day 5 morning, 50% on Day 5 afternoon. Continuous LLM-as-Judge monitoring throughout. Rollback remains instant at any point.
Day 7 — Full Migration
New model serves 100% of traffic
Full cutover to new model. Old model retained for 14 days for rollback availability. Operator receives completion notification with quality comparison. LLM Registry updated with new model as primary. Old model's adapter retained permanently.

LLM-as-Judge Evaluator #llm-as-judge

The LLM-as-Judge Evaluator is used in two contexts: validating new adapter versions before promotion to production, and evaluating candidate models during migration shadow testing. It uses a panel of three independent LLMs to score generated code, reducing single-model bias.

Evaluation Panel #judge-panel

Judge ModelWeightRationale
Claude Sonnet 4.640%Strong reasoning and code quality assessment. Primary judge with highest weight.
GPT-4o35%Independent perspective. Different training distribution reduces shared blind spots with Claude.
Gemini 1.5 Pro25%Third independent perspective. Trained with Google's different code corpus.

Using three independent judges with different training backgrounds reduces the risk of all judges sharing the same biases. A model that is subtly bad in a way Claude is blind to will likely be caught by GPT-4o or Gemini, and vice versa.

Scoring Criteria #judge-criteria

CriterionWeightWhat Is Evaluated
Correctness30%Does the code implement what the task descriptor specifies? Does it satisfy the acceptance criteria? Does it handle the edge cases listed?
Convention compliance25%Does the code follow the customer's established patterns as demonstrated in the training data? Correct naming, structure, error handling style.
Code quality20%Is the code readable, maintainable, and idiomatic for the language? No unnecessary complexity, no code smells, appropriate abstraction level.
Performance15%Does the implementation avoid obvious performance pitfalls? Appropriate data structures, no N+1 queries, no unnecessary allocations.
Security10%Does the code avoid common security mistakes? Input validation present, no injection vulnerabilities, no hardcoded secrets.

Position Bias Correction #bias-correction

LLMs exhibit position bias — they tend to prefer whichever code sample they see first, regardless of quality. The Evaluator corrects for this by evaluating each pair twice with the order reversed, then averaging the scores.

Evaluation run 1:  Judge sees [Model A output, Model B output]
                   Scores: A=0.82, B=0.76

Evaluation run 2:  Judge sees [Model B output, Model A output]
                   Scores: B=0.79, A=0.83

Position-corrected score:
  Model A: (0.82 + 0.83) / 2 = 0.825
  Model B: (0.76 + 0.79) / 2 = 0.775

Decision: Model A is better. Margin is sufficient (>0.02) to be
          meaningful rather than noise.

// Cost per comparison pair (with bias correction):
// 2 runs × 3 judges × ~1,500 tokens = ~9,000 tokens
// At blended judge pricing: ~$0.045 per comparison pair

A margin threshold of 0.02 is applied — if the position-corrected score difference between two models is less than 0.02, the models are considered equivalent and the current production model is retained (conservative default: do not change if not meaningfully better).
