The Eight Pipeline Agents
Full specification of every agent in the FORGE pipeline — inputs, outputs, behavior, failure modes, token budgets, JSON contracts, and language support.
Components: 07–14 Version: 1.0 Status: Draft May 2026

Overview & Pipeline Order #overview

The FORGE pipeline consists of eight agents that execute in a defined sequence. Each agent has a single, narrow responsibility. No agent does work outside its specification. The Master Scheduler dispatches agents and reads their results — agents never trigger each other directly.

The JSON Contract Principle #json-contract

Every agent receives a JSON task descriptor from its input queue and writes a JSON result payload to its output queue. No free text passes between agents. Every result must include a status field of either "success" or "failure". Any result that does not parse as valid JSON, or that is missing required fields, is treated as a failure — the Scheduler moves the task to SUSPENDED and alerts the operator immediately.

Agent Design Rule
An agent that cannot complete its work returns a well-formed failure JSON — it never crashes silently, never returns partial results without flagging them, and never calls another agent directly. All routing decisions belong to the Master Scheduler.

01 — Code Agent #code-agent

01
Code Agent
Component 07
LLM Powered Company Fine-Tuned GPU Required 4,096 Token Budget
Purpose
Generate all source code and unit tests for a given task or bug fix. The only agent that produces code.
Triggers on
Task status: QUEUED (feature tasks). Bug status: QUEUED (bug fix tasks). Highest priority QUEUED item is dequeued first.
LLM Model
Company fine-tuned adapter on Qwen2.5-Coder-32B (default). Falls back to Claude Sonnet API if GPU unavailable or task token estimate below API routing threshold.
Hardware
Tier 2: L40S 48GB VRAM ($1.57/hr). Tier 1: H100 80GB for complex architecture tasks. Per-developer dedicated droplet.
Token budget
4,096 output tokens per call. Hard limit enforced in API call. Complex tasks may be configured to 8,192 with explicit justification in task schema.
Heartbeat
Every 30 seconds. progress_note updated after every file written.
Checkpoint
MASTER_CONTEXT.md updated after every file committed to git branch.

Inputs and Outputs #code-inputs

Input: Full task descriptor JSON from the Redis work queue (see Spec A §JSON Interfaces for complete schema). The agent reads the task descriptor once at dequeue time and does not re-read it during execution. If context is needed mid-task, it reads from MASTER_CONTEXT.md.

Output: Result JSON placed on the result queue. On success: list of files written, commit SHA, token usage, cost, and duration. On failure: structured error with the reason the agent could not complete the task — never a partial result without explicit flagging.

Behavior #code-behavior

On dequeue, the Code Agent performs the following sequence:

  1. Read MASTER_CONTEXT.md for this task. If a previous agent crashed mid-task, determine which files are already complete and skip them.
  2. Read all input interfaces from the branch — import the traits, types, and APIs produced by dependency tasks.
  3. For each file in files_to_write: generate the implementation, write to the feature branch, commit, update MASTER_CONTEXT.md, emit heartbeat.
  4. Write unit test files simultaneously with implementation files — not as a separate pass. Tests are written file-by-file alongside their corresponding implementation.
  5. On completion of all files: write result JSON to output queue, update Jira status to CODE COMPLETE.

The agent generates code that strictly respects the out_of_scope field in the task descriptor. It does not add features that were not requested. It does not refactor adjacent code unless the task explicitly requires it. It does not change the interface of an existing module unless the task output interfaces require it.

Unit Test Authorship #code-tests

The Code Agent writes unit tests alongside source code — it does not wait for the Test Agent to write them. This is the correct design because the agent that understands the intent of the code is best positioned to write tests that verify that intent.

Test files are written to a parallel tests/unit/ directory mirroring the source structure. Each test file covers one source module. Tests must cover:

  • Every public function and method in the corresponding source file
  • All acceptance criteria listed in the task descriptor
  • All error states listed in the task description
  • Edge cases noted in the task's out-of-scope list (to assert they are NOT handled)

The Test Agent does not write tests. It runs the tests written by the Code Agent, measures coverage, and reports pass/fail. If a test written by the Code Agent is itself incorrect — asserts the wrong behavior — the Test Agent creates a bug ticket describing the discrepancy between the test assertion and the acceptance criterion, and the Code Agent fixes either the test or the implementation as appropriate.

Bug Dequeue Behavior #code-bugs

The Code Agent monitors both the feature task queue and the bug queue simultaneously. Bugs are treated as tasks — they have the same JSON descriptor structure, the same pipeline, and the same heartbeat/checkpoint requirements. The only differences are:

02 — Build Agent #build-agent

02
Build Agent
Component 08
Rule Engine First Haiku Fallback CPU Only 512 Token Budget
Purpose
Compile the code written by the Code Agent. Produce a structured JSON error report on failure. No LLM needed for ~80% of compile errors.
Triggers on
Task status: CODE COMPLETE. Dispatched immediately by Scheduler upon reading CODE COMPLETE result.
LLM Model
None for known error types (rule engine). Claude Haiku for unknown or ambiguous errors only.
Hardware

Token budget
512 output tokens. The Build Agent only needs to classify errors — it does not generate fixes.
Language agnostic

Rule Engine #build-rule-engine

Before calling Claude Haiku for any error, the Build Agent passes the error output through the rule engine. The rule engine is a library of regex patterns, error code matchers, and structured checks for the most common compile errors in each language. If a match is found, the error is classified and structured into JSON without any LLM call — at zero cost.

Lifetime / borrow errors (Rust)E0382, E0502, E0505, E0506Sometimes — complex borrow cases escalate to Haiku
Syntax errorAny language — unexpected token, missing bracketNo — file and line are sufficient
Missing trait implementationRust E0277, Java "does not implement interface"No
Ambiguous / novel errorAny error not matching a known patternYes — Claude Haiku classifies and structures it

03 — Security Agent #security-agent

03
Security Agent
Component 09
SAST CVE Scanning Secrets Detection SOC 2 Controls Creates Bug Tickets
Purpose
Scan every build for known vulnerabilities, exposed secrets, dangerous code patterns, license violations, and SOC 2 relevant control gaps. Create bug tickets for all findings. Block pipeline on Critical and High severity.
Triggers on
Every successful Build Agent result. Runs before Test Agent — security must pass before testing begins.
LLM Model
None for known CVEs and pattern matches (scanner tooling). Claude Haiku for contextual risk assessment of ambiguous findings.
Hardware
CPU only. Shared per tenant — not per developer. One Security Agent instance per tenant handles all developers' scans.
Scope
Scans only the files written or modified by the current task. Does not re-scan the entire codebase on every task.

Severity Routing #security-routing

SeverityPipeline ActionJira ActionCode Agent Action

Important — Medium Bug Triage
Medium and Low security findings are always visible in Jira but do not automatically become QUEUED for the Code Agent. This prevents the platform from autonomously making security tradeoff decisions — those decisions require human judgment. A tech lead or security reviewer triages Medium findings and moves them to QUEUED when they decide remediation is warranted.

04 — Test Agent #test-agent

04
Test Agent
Component 10
Evaluator Only Creates Bug Tickets Coverage Gating CPU Only
Purpose
Run the unit tests written by the Code Agent. Measure coverage. Create bug tickets for every failure. Evaluate results and route accordingly. The Test Agent does not write tests.
Triggers on
Task: Security Agent reports no Critical/High findings. Bug (re-verification): Code Agent reports FIX COMPLETE on a test failure bug.
LLM Model
None for test execution. Claude Haiku for classifying ambiguous test failures where the cause is not clear from the test output alone.
Hardware
CPU only for test execution. Uses the developer's droplet for language-specific test runner invocation.
Token budget
1,024 output tokens (Haiku only, for ambiguous failure classification).

Behavior and Coverage Gating #test-behavior

The Test Agent executes the following sequence:

  1. Run the full unit test suite using the language executor's test runner (same executor interface as the Build Agent).
  2. Parse all test results into a structured list of pass/fail per test case.
  3. Measure line and branch coverage using the executor's coverage tool.
  4. Compare coverage against the test_coverage_threshold in the task descriptor.
  5. For each failure: classify the failure type, create a Jira bug ticket, add it to the Code Agent's bug queue.
  6. Write result JSON to output queue with complete test summary.

Coverage gating: If coverage falls below the threshold, a coverage gap bug ticket is created regardless of whether all tests pass. A task where all tests pass but coverage is 72% against an 80% threshold is still a failing task. The coverage bug ticket describes which files and which branches lack coverage, so the Code Agent knows specifically what additional tests to write.

Bug Creation #test-bug-creation

One bug ticket is created per distinct failure. If 5 tests fail, 5 bug tickets are created. The Test Agent groups related failures — if 3 tests fail due to the same underlying cause (determined by shared stack trace prefix), they are grouped into one bug ticket with all 3 tests listed.

Failure TypeSeverityBug Ticket Content
Exception / panic during testP1Test name, exception type, stack trace, file and line, expected behavior from acceptance criterion
Assertion failure — wrong outputP2Test name, expected value, actual value, the specific assertion that failed, acceptance criterion being verified
Timeout — test did not completeP2Test name, timeout duration, last known operation before timeout, possible deadlock or infinite loop indication
Coverage gapP3Files below threshold, specific uncovered lines and branches, which acceptance criteria lack test coverage
Test itself incorrectP2Test name, the assertion that appears incorrect, the acceptance criterion it claims to verify, why the assertion conflicts with the criterion

05 — Performance Agent #performance-agent

05
Performance Agent
Component 11
Load Testing Creates Bug Tickets Per-Task Thresholds CPU Only
Purpose
Run load tests against the deployed container. Measure performance metrics against per-task thresholds. Create bug tickets for any metric that breaches its threshold.
Triggers on
Integration Test Agent reports all acceptance criteria verified. Runs as final validation before task is marked COMPLETED.
Load testing tool
k6 for HTTP/gRPC services. Custom harness for databases and libraries. Locust for Python services.
LLM Model
Claude Haiku for profiling data interpretation — identifying likely root cause of performance regression from metrics and stack traces.
Token budget
1,024 output tokens. Performance interpretation only — the agent does not generate fixes.

Metrics and Thresholds #perf-metrics

Thresholds are defined per task in the task descriptor's performance_thresholds field. Default thresholds are applied if not specified. The Performance Agent measures:

MetricDefault ThresholdMeasurement Method
p50 latency50msMedian response time across all requests in load test
p95 latency200ms95th percentile response time — most important SLA metric
p99 latency500msTail latency — long tail issues show here
Throughput (RPS)500 req/secMaximum sustained requests per second at target concurrency
Error rate<0.1%Percentage of requests returning 5xx or timeout under load
Memory usage<512MB RSSPeak resident memory during load test
CPU usage<80%Peak CPU utilization during load test
Memory leakNo growth >10% over 60 sec sustained loadRSS trend over time during extended load test

Load test profile: 30-second ramp from 0 to target concurrency (default: 100 virtual users), 60 seconds at target, 10-second ramp-down. Total test duration: approximately 100 seconds per endpoint tested.

Bug Creation #perf-bugs

One bug ticket is created per metric breach. Each ticket includes: the metric name, the measured value, the threshold value, the affected endpoint or operation, the load test configuration used, relevant profiling data (CPU flame graph if available, memory profile, slow query log if database involved), and Claude Haiku's interpretation of the likely root cause.

Breach SeverityConditionPriority
P1Metric exceeds 2× threshold, or error rate exceeds 1%, or service crashes under loadBlocker — blocks deployment
P2Metric between 1.2× and 2× thresholdHigh — blocks deployment
P3Metric between threshold and 1.2× threshold (marginal breach)Medium — does not block deployment, queued for next sprint

06 — Deploy Agent #deploy-agent

06
Deploy Agent
Component 12
No LLM Scripted Only Instant Rollback Human Gate for Prod
Purpose
Build a Docker image from the committed code, run it in the target environment, perform health checks, and report the container ID for rollback.
Triggers on
Test Agent reports all tests passing and coverage met. Security Agent has no blocking findings.
LLM Model
None. The Deploy Agent is fully scripted. Deployment is deterministic — no LLM judgment is needed or appropriate.
Hardware
CPU only. Docker daemon on the developer's droplet or a shared CI node.
Production gate
Staging deployment is automatic. Production deployment requires explicit human approval — the Deploy Agent pauses and posts an approval request to Jira and the developer dashboard.

Environments #deploy-environments

EnvironmentTriggerHuman Approval?Auto-Rollback?
DevelopmentAfter Build Agent success — deploy for Integration Test Agent to run againstNoYes — on health check failure
StagingAfter Test Agent and Security Agent passNoYes — on health check failure
ProductionAfter Performance Agent passes AND human clicks approve in dashboardYes — required, non-negotiableYes — automatic on health check failure

Rollback #deploy-rollback

On every successful deployment, the Deploy Agent stores the previous container ID in Redis under deploy:{task_id}:previous_container. If the health check fails after deployment, the rollback procedure is:

  1. Stop the new container immediately.
  2. Read the previous container ID from Redis.
  3. Start the previous container.
  4. Verify health check passes on the previous container.
  5. Report rollback completion to Scheduler.
  6. Scheduler moves task back to QUEUED and increments code failure retry counter.
  7. FORGE Bot adds Jira comment: "Deployment failed health check. Rolled back to previous version [container ID]. Task requeued. Attempt [N] of 3."

Rollback takes less than 30 seconds in all tested scenarios. The previous container is always kept running in a paused state until the new container passes its health check — cold start time is eliminated from the rollback path.

07 — Integration Test Agent #integration-agent

07
Integration Test Agent
Component 13
Acceptance Criteria Verifier Real Deployment LLM Powered 1,024 Token Budget
Purpose
Send real requests to the running deployment and verify that every acceptance criterion in the task descriptor is satisfied. Not just that tests pass — that the feature does what the product owner asked for.
Triggers on
Deploy Agent reports healthy container running in staging or development environment.
LLM Model
Claude Haiku to translate acceptance criteria into test scenarios and evaluate whether API responses satisfy each criterion.
Hardware
CPU only. Sends HTTP/gRPC requests to the deployed container.
Token budget
1,024 output tokens. Haiku evaluates responses against criteria — brief judgments, not code generation.

The Integration Test Agent reads the acceptance_criteria list from the task descriptor and generates a real test scenario for each criterion. For the cryptocurrency payment feature, it would: call the charge creation endpoint with a test BTC amount, verify the response contains a wallet address and amount in BTC, wait 15 minutes and verify the order expires, simulate a Coinbase webhook and verify order status changes, and verify that an expired order reverts to UNPAID rather than CANCELLED.

The agent uses the Coinbase Commerce testnet (or equivalent sandbox environment for other third-party services) — it never makes real financial calls. Sandbox credentials are injected from the customer's environment configuration.

On any criterion failure, a bug ticket is created with: the criterion text, the actual API response, what the expected response should be, and the specific discrepancy. These integration test bugs are Priority P1 — they mean the feature does not work as the product owner specified.

08 — Audit Agent #audit-agent

08
Audit Agent
Component 14
Rule Engine First Haiku Fallback Fix Spec Generator 1,024 Token Budget
Purpose
Called when a pipeline failure cannot be routed to a specialist agent. Reads logs and metrics, classifies the failure, and produces a structured JSON fix specification that is sent directly to the Code Agent.
Triggers on
Any agent reporting a failure that doesn't fit the standard Build/Test/Security/Performance routing. Also called when the Scheduler detects an unexpected pipeline state.
LLM Model
None for known error patterns (rule engine handles ~80%). Claude Haiku for unknown or novel failures.
Hardware
CPU only. Shared per tenant.
Token budget
1,024 output tokens. The Audit Agent classifies and structures — it does not generate fixes itself.
Log input limit
Maximum 50 lines of log sent per call. Logs are truncated and filtered to the most relevant lines before the API call.

Rule Engine #audit-rule-engine

The Audit Agent rule engine is a library of patterns matched against log lines, error codes, and metric anomalies. Each pattern maps to a known failure class and a structured fix specification template. When a pattern matches, the fix spec is generated without any LLM call.

Pattern CategoryExamplesLLM Needed?
Out of memoryOOM killer log lines, Java heap space errors, Rust allocation failureNo — known fix: increase memory limit or identify leak
Port conflict"Address already in use", "bind: address already in use"No — known fix: release port or change config
Missing environment variable"env var not set", "required env", KeyError on env lookupNo — the variable name is in the error message
Database connection refused"connection refused", "connection reset", timeout on DB connectNo — known fix: check connection string, check DB is running
Permission deniedFile permission errors, Docker capability errorsNo — known fix: adjust permissions or Dockerfile
Container crash loopExit code patterns, restart count in Docker logsSometimes — root cause varies; Haiku reads the crash logs
Novel or composite failureMultiple simultaneous errors, unknown error codesYes — Haiku reads the logs and produces the fix spec

Fix Spec Output #audit-output

The Audit Agent output is not a description of the problem — it is a structured fix specification the Code Agent can act on directly. The instructions array contains ordered steps. The do_not_touch array tells the Code Agent which files must not be modified during the fix — preventing the Code Agent from making well-intentioned changes that would break other parts of the system.

  "task_id":      "FORGE-291",

  "failure_class": "missing_environment_variable",
  "classified_by": "rule_engine",
  "instructions": [
    {
      "step": 1,
      "action": "add_env_var",
      "file":   "src/config.rs",
      "detail": "Add COINBASE_WEBHOOK_SECRET to the Config struct, read from std::env. Return ConfigError::MissingEnvVar if not set."
    },
    {
      "step": 2,
      "action": "update_docker_env",
      "file":   "Dockerfile",

      "step": 3,

    "src/payments/charge_service.rs",
    "src/payments/coinbase_client.rs"

Cost Design
The majority of agent work — build error classification, known security pattern matching, test result parsing, standard deployment — costs zero LLM tokens. LLM calls are reserved for work that genuinely requires language understanding: code generation, novel error classification, and acceptance criteria verification. This design keeps the average per-task LLM cost to approximately $0.05–0.15, dominated by the Code Agent.
